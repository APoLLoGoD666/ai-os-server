## PREAMBLE

R0 is the Runtime Specification Standard. It is the first document of the R-series and the only R-series document that defines no runtime. Every other R-series document (R1 through R16) defines one runtime. R0 defines the standard those documents must satisfy.

R0 exists because the constitutional architecture requires that runtime specifications be: structurally identical, constitutionally grounded, implementation-independent, mutually non-overlapping, and fully auditable. These requirements cannot be satisfied by convention or by example. They require a binding standard, established before any runtime specification is written, from which every runtime specification derives its structure.

R0 derives exclusively from D-2 through D8, A0, and A1. R0 introduces no new constitutional concepts. R0 introduces no implementation. R0 creates no new runtimes, no new authority, no new objects, no new ontology. R0 organizes pre-existing constitutional obligations into a mandatory documentation form.

A runtime specification that does not comply with R0 is not canonical. It has no constitutional standing. It cannot authorize implementation. It cannot be cited by other constitutional documents.

## PART 1 — DERIVATION BASIS AND NECESSITY PROOF

### 1.1 Why a Runtime Specification Standard is Required

D8 §1.1 establishes the Constitutional Implementation Boundary: the rule that constitutional concepts must be translated into implementation faithfully, completely, and without distortion. D8 Translation Invariant TI-1 (Translation Completeness) requires that every constitutional property defined in D-series and A-series must appear in a lower-layer specification with no loss of constitutional meaning. D8 TI-2 (Authority Preservation) requires that authority assignments established in D6 and instantiated in A0 are preserved through every layer of specification. D8 TI-3 (Object Integrity) requires that objects cannot lose their constitutional properties as they move through specification layers. D8 TI-4 (Temporal Ordering) and TI-5 (Loop Integrity) impose similar completeness requirements on temporal and loop specifications.

These five translation invariants create a necessary condition: if runtime specifications are produced without a common standard, no audit can verify that TI-1 through TI-5 are satisfied across the full R-series. One runtime specification might document temporal properties; another might omit them entirely. One might document authority with D6 citations; another might claim authority by assertion. The resulting collection of runtime specifications would be constitutionally non-comparable, non-auditable, and structurally incomplete.

D8 also establishes Constitutional Loop Invariants CLI-1 through CLI-4: no stage omission, no short-circuit, feedback completeness, temporal coherence. These invariants apply to the system as a whole — not to any single runtime in isolation. For CLI-1 through CLI-4 to be verifiable across the full system, each runtime specification must document its stage participation, its loop phase ownership, and its feedback obligations using a common format. Without that common format, CLI-1 through CLI-4 cannot be audited.

D8 further defines the Minimum Viable Constitutional System (MVCS): the minimum set of runtime properties that must be specified for the system to be constitutionally operable. The MVCS presupposes that each runtime has a specification. R0 defines what that specification must contain.

The necessity of R0 is therefore not a design preference. It is a logical consequence of D8's translation invariants, loop invariants, and MVCS requirements.

### 1.2 Derivation from A0's Runtime Decomposition

A0 derived 16 runtimes (RT-01 through RT-16) from D-2 through D8 by applying five derivation tests to 24 runtime candidates. For each of the 16 retained runtimes, A0 specified:

- Constitutional role
- Tier assignment
- Owned objects
- Consumed objects (inputs from other runtimes)
- Produced objects (outputs to other runtimes)
- Constitutional invariants
- Authority assignments (by AIR type from D6)
- Dependency list (which runtimes this runtime depends upon)
- Dependent list (which runtimes depend upon this runtime)

These A0-specified properties are necessary but not sufficient for a complete runtime specification. A0 establishes what each runtime is and what it owns. A0 does not specify: the runtime's internal state machine, its lifecycle phases, its failure modes, its recovery obligations, its audit requirements, its validation requirements, its execution position in canonical flows, its relationship to the Constitutional Loop, or its constitutional translation requirements. These additional properties are required for the R-series to serve as the complete specification layer above implementation.

R0 mandates the template by which A0's necessary properties are completed into sufficient specifications. Every A0-defined property has a corresponding mandatory section in R0's template. Every additional property required for implementation-facing completeness has a mandatory section in R0's template.

### 1.3 Derivation from A1's Interaction Architecture

A1 defined the complete interaction architecture between all 16 runtimes. For every pair of runtimes, A1 determined: whether interaction exists, its direction, its eight constitutional properties (P1 through P8), its blocking behavior, its rollback responsibility, its invariants, and its authorizing documents. A1 also defined: eight complete graphs, eight canonical execution orders, the 16×16 permission matrix, interaction classifications (Mandatory, Conditional, Forbidden), and Constitutional Loop cycle analysis.

A1's closure proof established that all interaction ambiguity is resolved. The R-series must not reopen that ambiguity. Every runtime specification must reference A1 for its interaction architecture and may not deviate from it.

R0 mandates that every runtime specification include an External Interactions section (RS-13) that maps bijectively to all A1 PAIRs involving that runtime. It mandates an Execution Position section (RS-30) that maps to A1's canonical execution orders. It mandates a Constitutional Loop Participation section (RS-29) that maps to A1's loop phase analysis. Through these mandatory sections, R0 ensures that A1's interaction architecture is preserved intact through the R-series.

### 1.4 The Bridge Function of R0

R0 bridges three layers:

**Above R0:** A-series (A0 runtime derivation, A1 interaction architecture) — defines what the runtimes are and how they interact at constitutional level.

**R0 itself:** Defines how each runtime must be specified — the mandatory structure, fields, standards, and certification requirements.

**Below R0:** R1 through R16 (individual runtime specifications) — apply R0's template to each specific runtime using A0 and A1 as content sources.

R0 is the only layer that performs this bridge function. Removing R0 would make R1 through R16 structurally arbitrary and constitutionally unverifiable.

### 2.2 The Authority Derivation Rule

**Rule ADR-1 (No Direct D-series Authority):** No runtime may derive constitutional authority directly from any D-series document. The authority derivation path is mandatory:

```
D6 (assigns authority types AIR-1 through AIR-5 to domains)
 ↓
A0 (instantiates authority assignments to specific runtimes)
 ↓
A1 (specifies how authority flows in interactions)
 ↓
R0 (mandates how each runtime documents its authority in RS-06)
 ↓
R1–R16 (document specific authority under R0 standard)
```

A runtime specification that claims authority by citing D6 directly, without tracing through A0's instantiation, violates Rule ADR-1. The A0 instantiation is the constitutional record of which runtime holds which authority. D6 defines the authority types; A0 determines their holders.

**Rule ADR-2 (Authority Not Self-Assigned):** No runtime specification may assign authority to its runtime that is not present in A0's authority relationship graph (A0 §4.3). Authority is assigned by the constitutional record, not by the R-series author.

**Rule ADR-3 (AIR-5 Non-Delegable):** RT-04's AIR-5 (Audit Authority) cannot be delegated to any other runtime. No runtime specification may claim AIR-5. No runtime specification may describe a mechanism by which RT-04 delegates its audit function.

**Rule ADR-4 (Authority Scope Binding):** The scope of authority claimed in RS-06 must be identical to the scope assigned in A0. A runtime specification that claims broader authority than A0 assigns is constitutionally invalid. A runtime specification that claims narrower authority than A0 assigns is constitutionally incomplete.

### 2.3 What a Runtime Specification Is

A Runtime Specification is a complete, constitutionally grounded, implementation-independent document that specifies one runtime's:

- Constitutional identity (RT-NN, name, tier, role)
- Constitutional basis (every D-series and A-series provision that governs it)
- Purpose (the constitutional function it fulfills)
- Scope (what is and is not within its constitutional boundary)
- Responsibility (the constitutional obligations it must fulfill)
- Authority (the AIR-type authority it holds, in which domains, under what conditions)
- Ownership (the constitutional objects it creates and is responsible for)
- Inputs (every object it receives, from which runtime, through which channel)
- Outputs (every object it produces, to which runtime, through which channel)
- Managed state (all state variables with constitutional classification)
- Internal processes (all constitutionally mandated internal operations)
- External interactions (all A1-defined interactions, with PAIR references)
- Lifecycle (all constitutional phases from activation through termination)
- State machine (all valid states and transitions)
- Entry and exit conditions (constitutional preconditions for each lifecycle phase)
- Preconditions and postconditions (per operation class)
- Invariants (continuously required constitutional properties)
- Failure modes (all constitutionally recognized failure states)
- Recovery obligations (constitutional recovery actions per failure mode)
- Audit requirements (what RT-04 audits about this runtime)
- Validation requirements (which validation checkpoints this runtime participates in)
- Observability metrics (what must be observable for constitutional audit)
- Dependencies and dependents (as specified in A0 and A1)
- Constitutional Loop participation (phase ownership per A1 §15.2)
- Execution position (step position in A0 §4.4 and A1 §12.x orders)
- Phase ownership (which Constitutional Loop phases this runtime primarily owns)
- Architectural boundaries (constitutional demarcation)
- Translation requirements (how D8's TI-1 through TI-5 apply)
- Implementation constraints (what implementation must satisfy, not how)
- Prohibited responsibilities (what this runtime must never do)
- Self-certification (CERT-01 through CERT-10 self-assessment)

All of the above is derived exclusively from D-2 through D8, A0, and A1. Nothing is invented in an R-series document.

### 2.4 What a Runtime Specification Is Not

A Runtime Specification is not any of the following:

**Not a software design document.** A runtime specification does not specify classes, modules, services, functions, or components.

**Not a technology selection document.** A runtime specification does not name, prefer, or recommend any programming language, framework, database, message queue, container, cloud provider, or any other technology.

**Not an API specification.** A runtime specification does not define endpoints, request formats, response formats, authentication mechanisms, rate limits, or any API contract.

**Not a database schema.** A runtime specification does not define tables, columns, indexes, foreign keys, or any storage schema.

**Not a process scheduling specification.** A runtime specification does not define thread pools, worker counts, scheduling policies, or concurrency mechanisms.

**Not a deployment guide.** A runtime specification does not define how a runtime is deployed, configured, scaled, or monitored in any infrastructure.

**Not a performance specification.** A runtime specification does not define latency targets, throughput requirements, resource limits, or any quantitative performance goal.

**Not an implementation plan.** A runtime specification does not define work items, sprints, milestones, or any project management artifact.

**Not a testing specification.** A runtime specification does not define test cases, test data, mocking strategies, or coverage requirements. (Certification requirements in RS-36 define constitutional certification criteria, not software tests.)

If a claimed runtime specification contains any of the above, it is constitutionally invalid and must be corrected before becoming canonical.

## PART 3 — RUNTIME CONSTITUTIONAL DEFINITIONS

This part defines 39 constitutional concepts that every runtime specification must address. Each definition states: what the concept is, its constitutional basis, how it must be documented in the runtime specification, and the completeness test.

### 3.1 Runtime Identity

**Definition:** The unique and immutable constitutional designation of a runtime within the APEX system. Runtime identity consists of: the runtime identifier (RT-NN format, zero-padded to two digits), the canonical name (as defined in A0), the tier assignment (T1 through T6), and the constitutional role statement.

**Constitutional basis:** A0 §3.x (one subsection per runtime), A0 §2.4 (tier structure).

**Documentation requirement:** RS-01 must state all four identity components. No component may be abbreviated, paraphrased, or inferred. The identifier, name, tier, and role must appear verbatim as defined in A0.

**Completeness test:** RS-01 is complete if and only if it contains exactly the RT-NN identifier, exactly the A0-defined canonical name, exactly the tier designation, and a role statement traceable to A0's constitutional role description for that runtime.

**Immutability rule:** Runtime identity may not be changed by any R-series document. A change to a runtime's identity requires an Amendment Process (D7 §6.1, RT-16).

### 3.2 Runtime Responsibility

**Definition:** The complete and exclusive set of constitutional obligations a runtime is required to fulfill. Responsibility is constitutional (not operational): it is what the runtime must do to satisfy the constitutional record, not how it does it.

**Constitutional basis:** A0 §3.x (responsibility per runtime), D8 MVCS (minimum obligations for constitutional operability).

**Documentation requirement:** RS-05 must enumerate every responsibility as a numbered obligation. Each obligation must cite its constitutional source (D-series provision, A0 section, or A1 PAIR). Responsibilities must be stated as constitutional obligations ("This runtime is constitutionally obligated to..."), not as design intentions.

**Exclusivity rule:** No two runtime specifications may claim the same responsibility. If responsibility overlap is detected between two R-series documents, both documents are constitutionally invalid at the point of overlap, and A0 must be consulted to resolve the boundary.

**Completeness test:** RS-05 is complete if: (a) every A0-defined obligation for this runtime appears as a numbered responsibility, (b) every responsibility has a constitutional citation, (c) no responsibility appears in any other runtime's RS-05.

### 3.3 Runtime Boundaries

**Definition:** The constitutional demarcation that separates what is inside a runtime's scope from what is outside. Boundaries have three components: (a) the interior — objects, states, and processes exclusively owned by the runtime; (b) the interface — objects and signals that cross the boundary (inputs from other runtimes, outputs to other runtimes); (c) the exterior — all constitutional content explicitly excluded from this runtime's responsibility.

**Constitutional basis:** A0 §3.x (boundary analysis per runtime), A1 §3.x (interaction pairs defining what crosses boundaries), A1 §14.3 (Forbidden Interactions defining what must not cross).

**Documentation requirement:** RS-32 (Architectural Boundaries) must enumerate all three boundary components. The interior is documented through RS-07 (Ownership) and RS-10 (Managed Objects). The interface is documented through RS-08 (Inputs), RS-09 (Outputs), and RS-13 (External Interactions). The exterior is documented through RS-35 (Prohibited Responsibilities).

**Completeness test:** RS-32 is complete if: (a) every object in RS-10 appears in the interior, (b) every interaction in RS-13 corresponds to an A1 PAIR at this boundary, (c) every Prohibited Responsibility in RS-35 is traceable to an A1 Forbidden Interaction or an A0 boundary determination.

### 3.4 Runtime Ownership

**Definition:** The set of constitutional objects a runtime creates, is responsible for, and serves as the provenance anchor for. Ownership is not possession or storage — it is constitutional authorship. An owned object's validity is the runtime's constitutional responsibility.

**Constitutional basis:** A0 §3.x (owned objects per runtime), D8 §4.1 (17 canonical object types), A1 §9.1 (provenance rules PA-1 through PA-5), D4 §2.1 (KMP — cross-runtime mutation of owned objects requires Kernel Mediation).

**Documentation requirement:** RS-07 must list every object type this runtime owns, the D8 canonical object type (or derivation from a canonical type), the conditions under which new instances are created, the provenance anchor format (referencing A1 §9.2 provenance chain), and the cross-runtime mutation rule (citing KMP where applicable).

**Cross-ownership prohibition:** No runtime may claim ownership of an object owned by another runtime. Cross-runtime mutation of another runtime's objects without Kernel Mediation is a constitutional violation (D4 §2.1, A1 CC-1).

**Completeness test:** RS-07 is complete if every A0-listed owned object type for this runtime appears with: D8 canonical type reference, creation conditions, provenance anchor specification, and mutation rules.

### 3.5 Runtime Authority

**Definition:** The authority types from D6 (AIR-1 through AIR-5) that a runtime holds, specifying the domain(s) in which each authority type applies and the conditions under which each authority may be exercised.

**Constitutional basis:** D6 §3.1 (authority type definitions), D6 §3.4 (AIR-5 independence requirement), A0 §4.3 (authority relationship graph), A1 §5.1 (authority graph), A1 §5.2 (authority conflict resolution), Rule ADR-1 through ADR-4 (this document, Part 2.2).

**Authority types:**
- AIR-1 (Observation Authority): authority to register and validate observations within a domain
- AIR-2 (Interpretation Authority): authority to transform evidence into knowledge or understanding
- AIR-3 (Decision Authority): authority to form constitutionally binding decisions
- AIR-4 (Projection Authority): authority to cross the Projection Boundary (D5 §1.1)
- AIR-5 (Audit Authority): supreme authority to observe all operations; held exclusively by RT-04; non-delegable

**Documentation requirement:** RS-06 must state: for each AIR type held, (a) the authority type, (b) the domain(s) in which it applies, (c) the A0 §4.3 reference that instantiates this authority to this runtime, (d) the conditions under which it may be exercised, (e) the runtimes whose authority this runtime is subordinate to, and (f) the runtimes whose authority is subordinate to this runtime's.

**Completeness test:** RS-06 is complete if the authority claimed exactly matches A0's authority relationship graph for this runtime — no more, no less — with a citation for each authority claim.

### 3.6 Runtime Obligations

**Definition:** The mandatory constitutional actions a runtime must perform. An obligation is non-optional: failure to fulfill an obligation is a constitutional violation, not an operational error. Obligations arise from: D-series mandates that apply to this runtime's domain, A0-defined responsibilities, A1 mandatory interactions (A1 §14.1), and D8 MVCS requirements.

**Constitutional basis:** D4 §2.1 (KMP obligations for Class A runtimes), D8 CLI-1 through CLI-4 (loop obligations), D6 §3.4 (AIR-5 observation obligations for RT-04), A1 §14.1 (mandatory interactions table).

**Documentation requirement:** Obligations appear across multiple RS sections: constitutional obligations to gate (RS-16 Entry Conditions), to produce objects (RS-09), to admit operations (RS-12), to close feedback loops (RS-29), to accept audit (RS-23). RS-05 (Responsibility) provides the master list from which all obligation instances derive.

**Distinction from guarantees:** An obligation is what a runtime must do. A guarantee is what other runtimes may rely on this runtime doing. Obligations bind the runtime; guarantees bind the relationship. Both must be documented.

### 3.7 Runtime Guarantees

**Definition:** The constitutional commitments a runtime makes to all runtimes that depend upon it. A guarantee is: "If this runtime fulfills its obligations, then the stated property holds, and dependent runtimes may constitutionally rely on it." Guarantees are derived from the interaction properties defined in A1 (specifically the postconditions for each interaction).

**Constitutional basis:** A1 §3.x (postconditions per interaction pair), A0 §4.1 (dependency graph — a dependency implies the dependent relies on a guarantee).

**Documentation requirement:** RS-19 (Postconditions) documents the guarantees this runtime provides per operation class. RS-27 (Runtime Dependents) cross-references the dependents who rely on each guarantee. Each guarantee must state: the guaranteed property, the condition under which it holds, and the dependent runtimes that rely on it.

**Guarantee failure:** When a runtime cannot fulfill a guarantee (e.g., due to failure), it must activate its failure mode (RS-21) and execute its recovery obligations (RS-22) to restore the guarantee or notify dependents that the guarantee is suspended.

### 3.8 Runtime Assumptions

**Definition:** The constitutional conditions a runtime relies upon from other runtimes and from the environment. An assumption is: "This runtime's correct operation presupposes that the stated condition holds." If an assumption is violated, the runtime must detect the violation and enter its failure mode.

**Constitutional basis:** A0 §4.1 (dependency graph — a dependency implies an assumption about the dependency's availability and correct function), A1 §3.x (preconditions per interaction pair — a precondition at an interaction is an assumption).

**Documentation requirement:** RS-18 (Preconditions) and RS-26 (Runtime Dependencies) together document assumptions. Each assumption must state: the assumed property, the runtime that is expected to guarantee it, and the failure mode triggered if the assumption is violated.

**Assumption verification:** Assumptions must be verified at runtime entry conditions (RS-16) and at each interaction precondition (A1 P7 blocking behavior). A runtime that proceeds without verifying assumptions is in violation of CLI-1 (no stage omission, D8).

### 3.9 Runtime Invariants

**Definition:** Properties that must hold continuously during all phases of runtime operation. Unlike preconditions and postconditions (which hold at specific points), invariants are always-true obligations. An invariant violation at any point during operation is a constitutional failure.

**Constitutional basis:** D4 §3.3 (gate invariants — all 6 gates must be traversed in sequence), D5 §4.1 (12 Projection Invariants for projection runtimes), D8 INV-1 through INV-7 (system invariants), A0 §3.x (per-runtime invariants), A1 §2.3 (six constitutional constraints CC-1 through CC-6).

**Invariant naming:** Runtime-specific invariants are named RTxx-INV-NN where xx is the zero-padded runtime number and NN is the invariant sequence number. Example: RT03-INV-01. Inherited invariants retain their source naming (CLI-1, PI-1, INV-1, CC-1, etc.).

**Documentation requirement:** RS-20 must enumerate all invariants applicable to this runtime, classified as: (a) system invariants inherited from D-series (cited by source), (b) A0-defined invariants for this runtime, (c) runtime-specific invariants derived from A1 interaction constraints, (d) Constitutional Loop invariants (CLI-1 through CLI-4) as they apply to this runtime's loop participation.

**Completeness test:** RS-20 is complete if: every A0-listed invariant for this runtime appears, every applicable D8 INV-N appears, every applicable D4/D5 invariant appears, and every A1 CC-N constraint applicable to this runtime appears.

### 3.10 Runtime Inputs

**Definition:** Every object, signal, or state that a runtime receives from another runtime or from external sources as part of its constitutional operation. An input is defined by: source runtime (or external source), object type (from D8 §4.1 canonical types), constitutional channel (Class A through RT-03, Class B direct, or AIR-5 audit), and the precondition for acceptance.

**Constitutional basis:** A0 §3.x (consumed objects per runtime), A1 §3.x (object ownership P4 and direction P1 per interaction pair), D4 §3.1–3.2 (Class A and Class B channel definitions).

**Documentation requirement:** RS-08 must enumerate every input in tabular form with columns: Input ID, Source Runtime, Object Type, Channel (Class A / Class B / AIR-5), A1 PAIR reference, Acceptance Precondition, Rejection Consequence. No input may be undeclared.

**Completeness test:** RS-08 is complete if: every A0-listed consumed object for this runtime appears, every A1 PAIR where this runtime is the receiving party has an entry in RS-08, and every entry has all required columns populated.

### 3.11 Runtime Outputs

**Definition:** Every object, signal, or state that a runtime produces and delivers to another runtime or to external systems as part of its constitutional operation.

**Constitutional basis:** A0 §3.x (produced objects per runtime), A1 §3.x (object ownership P4 and direction P1 per interaction pair).

**Documentation requirement:** RS-09 must enumerate every output in tabular form with columns: Output ID, Destination Runtime(s), Object Type, Channel, A1 PAIR reference, Delivery Postcondition, Failure Mode if delivery fails. No output may be undeclared.

**Completeness test:** RS-09 is complete if: every A0-listed produced object for this runtime appears, every A1 PAIR where this runtime is the initiating party has an entry in RS-09, and every entry has all required columns populated.

### 3.12 Runtime State

**Definition:** The complete set of state variables a runtime maintains across its operation. State is classified as: Constitutional State (state whose mutation requires Kernel Mediation per D4 §2.1 and affects the Reality Fabric), Operational State (state internal to the runtime that affects its function but does not directly commit to the Reality Fabric), and Ephemeral State (state that exists only within the scope of a single operation and is not persisted).

**Constitutional basis:** D4 §4.1 (committed state goes to RT-05 via RT-03 Stages 8+9), D3 (Reality Fabric state rules), A0 §3.x (state ownership per runtime).

**Documentation requirement:** RS-11 must enumerate all state variables with: state ID, state name, classification (Constitutional/Operational/Ephemeral), permissible values or value range, mutability conditions (what triggers mutation), and the constitutional authority required to mutate. Constitutional State variables must additionally cite the KMP channel through which mutations are admitted.

**Completeness test:** RS-11 is complete if every state variable the runtime maintains is enumerated and classified, and every Constitutional State variable cites its KMP mutation path.

### 3.13 Runtime Transitions

**Definition:** All valid state transitions the runtime may undergo, with full constitutional characterization. A transition is: a change from one valid state to another, triggered by a constitutional event, requiring specific authority, with a defined rollback path if the transition fails.

**Constitutional basis:** D4 §4.1 (10-Stage Lifecycle as the canonical transition model for Class A operations), A1 §15 (Constitutional Loop cycle transitions), D4 §5 (suspension type transitions).

**Documentation requirement:** RS-15 (State Machine) must document all transitions as a state transition table with: Source State, Trigger, Target State, Required Authority (citing D6 AIR type), Blocking Behavior (per A1 §2.5 definitions), Rollback Path on failure.

**Forbidden transitions:** RS-15 must also enumerate all constitutionally forbidden transitions (states that must never follow each other) with their constitutional basis.

### 3.14 Runtime Lifecycle

**Definition:** The complete sequence of constitutional phases from activation through termination, including all intermediate phases, all re-entry points (for recursive runtimes), and all suspension entry/exit points.

**Constitutional basis:** D4 §4.1 (10-Stage Lifecycle for Class A operations), D4 §5 (3 suspension types: Type A Operational, Type B Authority, Type C Domain Processing), D8 §2.1 (Constitutional Loop as the overarching lifecycle framework), A1 §12 (canonical execution orders for each process type).

**Documentation requirement:** RS-14 must document the runtime's lifecycle in sequential phases, with each phase stating: phase name, phase entry condition, constitutional activities within the phase, phase exit condition, the Constitutional Loop phase(s) this runtime lifecycle phase corresponds to, and which A1 canonical execution order contains this phase.

**Special cases:** RT-15 (Domain Runtime, 12 instances) must document the lifecycle of the archetype plus the instantiation lifecycle. RT-16 (Amendment Runtime) must document the event-driven activation lifecycle (not always-active).

### 3.15 Runtime Activation

**Definition:** The constitutional conditions under which a runtime transitions from inactive to active. Activation is not a technical startup; it is the satisfaction of constitutional preconditions that permit the runtime to begin its obligations.

**Constitutional basis:** A0 §4.4 (33-step execution order — when a runtime's steps begin), D4 §3.3 (Gate sequence — a runtime may not act until its gate preconditions are satisfied), D7 §6.1 (Amendment Runtime activated by RT-11 proposal).

**Documentation requirement:** RS-16 (Entry Conditions) must enumerate all activation preconditions. Each precondition must state: what must be true, which runtime guarantees it, and what happens if the precondition cannot be satisfied.

**Activation prohibition:** A runtime that activates without its preconditions being satisfied is in constitutional violation of D8 CLI-1 (no stage omission). This violation must be documented as a failure mode in RS-21.

### 3.16 Runtime Termination

**Definition:** The constitutional conditions under which a runtime transitions from active to inactive or to a suspended state. Termination may be: normal (all obligations fulfilled), suspended (one of three D4 suspension types), or failed (a constitutional failure condition that cannot be recovered within the runtime).

**Constitutional basis:** D4 §5 (3 suspension types), A1 §14.4 (Loop-Terminating interactions — operations rejected at RT-03 terminate the loop for that operation), D7 §5.1 (CUM Degradation Protocol — may suspend domain processing).

**Documentation requirement:** RS-17 (Exit Conditions) must enumerate all termination conditions, classify each as normal/suspended/failed, specify the suspension type (A/B/C) where applicable, and specify the post-termination state of all Constitutional State variables.

**Suspension handling:** Suspended runtimes must document: what triggers each suspension type, what state is preserved during suspension, what conditions permit resumption, and which runtime has authority to authorize resumption.

### 3.17 Runtime Persistence

**Definition:** The constitutional classification of what state the runtime persists across: individual operations, full Constitutional Loop cycles, suspension events, and system restart.

**Constitutional basis:** D4 §4.1 (Stage 9 atomic commit — committed state persists in RT-05), D3 (Reality Fabric as the constitutional persistence medium), A1 §7.1 (Mutation Ownership Table — what each runtime may persist).

**Documentation requirement:** RS-11 (Managed State) documents persistence through the state classification (Constitutional State persists in RT-05; Operational State persists in the runtime's own operational store; Ephemeral State does not persist). RS-14 (Lifecycle) documents which state persists across each lifecycle transition.

## PART 5 — MANDATORY STANDARDS

All standards in this part are binding on every runtime specification. Deviation from any standard renders the non-compliant provision constitutionally inadmissible.

### 5.1 Naming Standards

**NS-1:** All concepts must be named with terms drawn from the D-series constitutional record, A0, A1, or R0. Invented terminology is constitutionally inadmissible.

**NS-2:** Concept names must be unambiguous. Names referring to two different constitutional concepts must be disambiguated with a qualifying prefix (e.g., "Constitutional State" vs. "Operational State").

**NS-3:** No implementation terminology may appear as a concept name. Terms such as "service," "microservice," "endpoint," "handler," "worker," "job," "queue," "topic," "event bus," "repository," "DAO," "entity," and "DTO" are constitutionally inadmissible.

**NS-4:** When referring to a D-series constitutional concept, use the exact name from the defining document on first reference. Abbreviation (e.g., KMP) is permitted after the first use marks it with "(KMP)".

## PART 6 — RUNTIME QUALITY REQUIREMENTS

A runtime specification is canonical only when it satisfies all 10 quality requirements. These are constitutional completeness criteria, not style guidelines.

### 6.1 RQ-1 — Complete

**Criterion:** Every section RS-01 through RS-36 is present, fully populated with substantive constitutionally grounded content, and contains zero placeholder provisions.

**Constitutional Basis:** D8 TI-1 (translation completeness); D8 MVCS.

**Test:** Read every section. Flag any section that is absent, contains a placeholder ("TBD," "see implementation," etc.), or does not address the section's constitutional purpose. One flag = FAIL.

**Violation:** Absent sections; placeholder provisions; sections populated with off-purpose content.

### 6.2 RQ-2 — Minimal

**Criterion:** No provision is redundant. Every provision serves a distinct constitutional purpose.

**Constitutional Basis:** D-1 Rule DR-2 (formalization narrows, does not expand); D8 PROH-1.

**Test:** For every provision: "Does removing this provision reduce constitutional information content?" If no: the provision is redundant and must be removed or consolidated.

**Violation:** Provisions that duplicate other sections without adding constitutional specificity; provisions that state D-series facts without applying them to this runtime.

### 6.3 RQ-3 — Non-overlapping

**Criterion:** This runtime's responsibility, ownership, and authority do not overlap with any other runtime specification.

**Constitutional Basis:** A0 §2.2 (non-overlap survivorship test); A1 §14.3 (forbidden interactions enforce non-overlap).

**Test:** For every responsibility in RS-05, owned object in RS-07, and authority in RS-06: verify no other runtime's corresponding sections claim the same item. Any overlap = FAIL.

**Violation:** Two runtime specifications claiming the same responsibility, owned object, or AIR authority in the same domain.

### 6.4 RQ-4 — Constitutionally Grounded

**Criterion:** Every provision has a traceable constitutional basis in D-2 through D8, A0, or A1. A provision without a citation is inadmissible.

**Constitutional Basis:** D-1 Axiom A-DA-1 (every proposition must derive from constitutional source).

**Test:** For every provision: verify a constitutional citation exists in RS-02 and is accurate. One uncited provision = FAIL.

**Violation:** Any claim without traceable constitutional citation; any citation that does not support the claim it justifies.

### 6.5 RQ-5 — Implementation Independent

**Criterion:** No provision specifies an implementation mechanism. The specification is satisfiable by multiple completely different technical implementations.

**Constitutional Basis:** D8 §1.1 (Implementation Boundary); D8 PROH-1 through PROH-9.

**Test:** For every provision: "Does this specify HOW or WHAT?" HOW = FAIL. Secondary: "Could two different technical implementations each satisfy this provision?" No = FAIL.

**Violation:** Any provision naming a storage mechanism, algorithm, protocol, data format, technology, framework, or language.

### 6.6 RQ-6 — Technology Independent

**Criterion:** No technology name, framework, protocol, language, database, or computational paradigm appears in the specification.

**Constitutional Basis:** D8 PROH-1.

**Test:** Enumerate all nouns and proper nouns. Flag any naming a technology, product, framework, protocol, or paradigm. One flag = FAIL.

**Violation:** Programming languages, databases, message brokers, protocols, containers, cloud platforms, or computational paradigms named as requirements.

### 6.7 RQ-7 — Fully Auditable

**Criterion:** RT-04 can audit compliance with every provision using only the mechanisms defined in RS-23 and RS-25.

**Constitutional Basis:** D6 §3.4 (AIR-5); A1 §14.1 (RT-04 audit mandatory); D8 TI-1.

**Test:** For every provision: "Can RT-04 determine whether this is being satisfied using only RS-23 and RS-25?" No = FAIL.

**Violation:** Any provision that cannot be observed or verified through RS-23 (Audit Requirements) and RS-25 (Runtime Metrics).

### 6.8 RQ-8 — Fully Traceable

**Criterion:** Every object produced traces through a complete provenance chain. Every authority exercise traces to D6 through A0. Every interaction traces to an A1 PAIR.

**Constitutional Basis:** A1 §9.1 (PA-1 through PA-5); D6 §3.1 (authority must be constitutionally assigned); A1 §3.x (interactions must correspond to PAIRs).

**Test:** For every RS-09 output: trace through RS-08 and RS-07 to verify provenance anchoring per A1 §9.2. For every RS-06 authority: trace to D6 through A0 §4.3. For every RS-13 interaction: verify A1 PAIR reference is accurate. Any untraceable item = FAIL.

**Violation:** Objects without provenance chains; authority without D6-to-A0 trace; interactions without A1 PAIR reference.

### 6.9 RQ-9 — Recursively Complete

**Criterion:** The specification is complete with respect to all constitutionally authorized recursive structures this runtime participates in.

**Constitutional Basis:** A1 §11.1 (authorized recursion); A1 §11.2 (forbidden recursion FR-1 through FR-4); A1 §11.3 (Reality Feedback Loop).
