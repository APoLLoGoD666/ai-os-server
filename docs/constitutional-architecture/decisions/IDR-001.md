## Decision

**The canonical directory for all constitutional object type definitions is `lib/constitutional-types/`.**

All 35+ constitutional object type schema files will be created in `lib/constitutional-types/` and exported through `lib/constitutional-types/index.js`. The path `lib/runtime/types/` will not be used for constitutional type definitions.

---

## Context: The Contradiction

Two I-series planning documents specify different canonical paths for constitutional object type definitions.

**I0-IMPLEMENTATION-ROADMAP.md** (W1-01 through W1-12): specifies `lib/runtime/types/` as the location for all constitutional object type files.

Examples from I0-ROADMAP:
- W1-01: `lib/runtime/types/identity-record.js`
- W1-02: `lib/runtime/types/authority-record.js`
- W1-03: `lib/runtime/types/change-record.js`
- W1-04: `lib/runtime/types/historical-state-record.js`

**I1-IMPLEMENTATION-ARCHITECTURE.md** (Part 9): specifies `lib/constitutional-types/` as the canonical directory.

Examples from I1-ARCHITECTURE:
- §9.1: `lib/constitutional-types/identity-record.js`
- §9.2: `lib/constitutional-types/authority-certificate.js`
- §9.3: `lib/constitutional-types/change-record.js`

These two documents cannot both be correct. The canonical path must be one of the two options. This IDR resolves the conflict.

---

## Options Considered

### Option 1: `lib/runtime/types/` (I0-ROADMAP path)

**Path:** `lib/runtime/types/[type-name].js`

**Rationale for option:** The I0-ROADMAP is the earlier planning document and uses a directory (`lib/runtime/`) that already exists in the repository. Types would co-locate with other runtime implementation artifacts under `lib/runtime/`.

**Reason rejected:**

1. **Ontological confusion.** Constitutional object types are stable ontology definitions — they specify WHAT a thing is, not HOW a runtime implements it. Co-locating them under `lib/runtime/types/` implies they are runtime implementation artifacts, which they are not. A `ChangeRecord` type schema is owned by the constitutional specification of RT-05; it is not an artifact of the runtime execution mechanism.

2. **Consumption boundary violation.** Multiple runtimes consume the same constitutional types. `HistoricalStateQueryResult` is produced by RT-07 and consumed by RT-03. If it lives in `lib/runtime/types/`, it has an ambiguous owner — does it belong to the runtime that produces it or the one that consumes it? `lib/constitutional-types/` makes the shared, cross-runtime nature of these definitions explicit.

3. **Migration clarity.** The I1-REPOSITORY-MIGRATION-PLAN.md classifies `lib/constitutional-types/` as a CREATE artifact (new directory). If the path were `lib/runtime/types/`, new type files would be mixed into an existing directory containing pre-constitutional runtime artifacts, making the migration boundary unclear.

4. **I1 is the superseding document.** I1-IMPLEMENTATION-ARCHITECTURE.md was produced after I0-IMPLEMENTATION-ROADMAP.md as the detailed engineering blueprint. Where I0 and I1 conflict on implementation detail (not on constitutional requirements), I1 governs.

### Option 2: `lib/constitutional-types/` (I1-ARCHITECTURE path) ← CHOSEN

**Path:** `lib/constitutional-types/[type-name].js`

**Rationale for selection:**

1. **Semantic precision.** The directory name makes explicit that these files contain constitutional type definitions — not runtime logic. Engineers navigating the codebase will immediately understand the purpose of this directory.

2. **Constitutional authority alignment.** D8 §4.2 requires that constitutional objects be "accessible as first-class entities." A dedicated directory for constitutional types makes this accessibility explicit and enforces it architecturally. Runtime modules import from this layer; they do not own it.

3. **Ownership clarity.** The `lib/constitutional-types/` structure implies that type definitions are owned by the constitutional specification layer, not by any particular runtime's implementation. This correctly models the reality that object type schemas derive from the certified R-series specifications, which are authoritative and frozen.

4. **Future migration resilience.** If a runtime implementation is refactored or replaced, the constitutional type definitions it consumes remain stable in `lib/constitutional-types/`. They do not move when the runtime moves.

5. **Separation of concerns.** `lib/constitutional-types/` contains ontological definitions. `lib/runtime/` contains behavioral implementations. `lib/[runtime-name]/` contains per-runtime logic. These three concerns must remain separate.

---

## Constitutional Compliance Confirmation

This decision does not alter any observable constitutional behavior. It determines where type schema definitions physically reside in the file system. The constitutional specification (which defines WHAT the types are) is unchanged. The runtime specifications (which define HOW runtimes consume these types) are unchanged. This is a pure implementation path decision with no constitutional consequence.

The chosen path (`lib/constitutional-types/`) is fully consistent with D8 §4.2's requirement that constitutional objects be accessible as first-class entities — a dedicated, named directory achieves this more directly than a subdirectory under `lib/runtime/`.

---

## Migration Impact

**All I1 and I2 documents already use `lib/constitutional-types/` consistently.** No documents require retroactive changes as a result of this decision.

The I0-ROADMAP.md references to `lib/runtime/types/` are superseded by this IDR. Engineers executing Wave 1 tasks must follow the I1-IMPLEMENTATION-SEQUENCING.md task definitions (which use `lib/constitutional-types/`), not the I0-ROADMAP.md file path references.

**`lib/runtime/types/` may still be used for non-constitutional implementation objects** (runtime-internal data structures that are not constitutional object types). This IDR applies only to the 35 canonical constitutional object types defined in the frozen certification baseline.
