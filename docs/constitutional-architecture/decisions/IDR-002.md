## Decision

**RT-02 authority concerns are realized in a dedicated `lib/authority/` directory containing three files with separated responsibilities:**

- `lib/authority/type-registry.js` — authority type constants (AIR-1 through AIR-5 from D6 §4.2–4.6)
- `lib/authority/authority-resolution.js` — authority resolution and delegation logic
- `lib/authority/authority-resistance.js` — authority resistance evaluation (AIR-N integrity rules from D6 §4.7)

The existing file `lib/constitution/authority-resistance.js` is migrated into this structure. It is not expanded in-place.

---

## Context: The Contradiction

Two I-series planning documents specify different structures for the RT-02 authority implementation.

**I0-IMPLEMENTATION-GAP-REGISTER.md (GAP-02-001):** Specifies that the new authority type registry should be created at `lib/authority/type-registry.js`. This implies a dedicated `lib/authority/` directory.

**I1-IMPLEMENTATION-ARCHITECTURE.md (Part 3, Constitutional Foundation section):** Specifies that RT-02 is implemented at `lib/constitution/authority-resistance.js` — an existing file — and proposes expansion of that file to add AIR type definitions.

These approaches cannot both be followed simultaneously. Expanding `lib/constitution/authority-resistance.js` would mix authority type definitions with authority resistance evaluation in a single file, which is both structurally unclear and fragile to future change.

---

## Options Considered

### Option 1: Expand `lib/constitution/authority-resistance.js` (I1-ARCHITECTURE approach)

**Path:** Add authority type constants and resolution logic to the existing `lib/constitution/authority-resistance.js` file.

**Reason rejected:**

1. **Single-responsibility violation.** `authority-resistance.js` is named for and built around the authority resistance evaluation function — the D6 §4.7 AIR-N integrity rules. Adding authority type definitions (D6 §4.2–4.6) to this file conflates two distinct constitutional concepts. C0-MANIFEST §5.2 item 7 explicitly warns: "D6 §4.2–4.6 AIR-N = five authority types; D6 §4.7 AIR-N = Authority Integrity Rules. These are distinct systems; do not conflate."

2. **Growing file scope.** Adding type constants, delegation logic, and resolution logic to `authority-resistance.js` would produce a file that implements four distinct responsibilities. This makes the file difficult to understand and maintain, and makes future constitutional changes (e.g., adding a new authority type via RT-16 amendment) harder to locate and apply.

3. **Constitutional clarity risk.** If authority type definitions and authority integrity rules share a module, an implementer modifying authority type constants may inadvertently affect integrity rule evaluation. These two systems must remain separable.

### Option 2: `lib/authority/` directory with separated files (I0-GAP-REGISTER approach, extended) ← CHOSEN

**Structure:**
- `lib/authority/type-registry.js` — defines and exports the five D6 §4.2–4.6 authority type constants
- `lib/authority/authority-resolution.js` — authority delegation resolution and chain validation
- `lib/authority/authority-resistance.js` — the AIR-N integrity rules from D6 §4.7; migrated from `lib/constitution/authority-resistance.js`

**Rationale for selection:**

1. **Constitutional respect.** C0-MANIFEST §5.2 item 7 identifies the conflation of authority types (§4.2–4.6) with authority integrity rules (§4.7) as a known risk. The three-file structure structurally prevents this conflation.

2. **D6 alignment.** D6 has two clearly distinct systems: the five authority types (§4.2–4.6) and the Authority Integrity Rules (§4.7). A directory with a file for each constitutional concept provides one-to-one traceability from specification to code.

3. **Migration safety.** The existing `lib/constitution/authority-resistance.js` is preserved by migrating it (not deleting it) to `lib/authority/authority-resistance.js`. Its existing callers must be updated, but the logic is preserved intact. This satisfies I2-MIGRATION-CONTROL-SYSTEM.md Rule MP-2 (no legacy removal without migration classification).

4. **I0-GAP-REGISTER basis.** GAP-02-001 explicitly proposes `lib/authority/type-registry.js` as the gap remediation target. Adopting this path resolves the gap while extending it to cover all three authority concerns.

5. **Separation enables testability.** Each of the three files can be unit-tested independently. Type registry tests, resolution tests, and integrity rule tests do not require each other.

## Migration Note: `lib/constitution/authority-resistance.js`

The existing `lib/constitution/authority-resistance.js` will be migrated to `lib/authority/authority-resistance.js` during Wave 2 implementation. The migration process:

1. Create `lib/authority/authority-resistance.js` with the same logic as the current file
2. Update all callers to require from the new path
3. Verify no callers remain referencing the old path
4. Remove `lib/constitution/authority-resistance.js` (or leave as a re-export stub with a deprecation notice during the transition period)

This migration is classified as Migration Decision Class C (per I2-IMPLEMENTATION-GOVERNANCE-MODEL.md §2.3). The ledger entry for `lib/constitution/authority-resistance.js` will be updated to state MIGRATED when complete.

**TCL note:** If an immediate migration of all callers of `lib/constitution/authority-resistance.js` is infeasible in Wave 2, a Temporary Compatibility Layer (Class E) may be introduced at the original path re-exporting from the new path. The TCL removal condition is: all callers updated to reference `lib/authority/authority-resistance.js`. This TCL must be documented in the Implementation Ledger per Rule TCL-1.

---

## Constitutional Compliance Confirmation

This decision does not alter any observable constitutional behavior. It determines the module structure for RT-02 implementation artifacts. The constitutional specification of RT-02 (R2-v1.0-canonical.md) specifies the authority types and integrity rules; this IDR only determines where those are implemented in the file system. The authority resolution logic, the five D6 authority type constants, and the AIR-N integrity rules are all preserved — they are restructured, not removed or altered.

The three-file structure does not introduce any new constitutional behavior. It reorganizes existing and planned behavior to reflect the constitutional document structure more precisely.
