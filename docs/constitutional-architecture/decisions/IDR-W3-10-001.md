## Executive Summary

T3-10 (EvidenceObject Wiring) was halted at Phase 0 by three blocking constitutional prerequisites absent from the current system:

1. **ObservationRecord ID not accessible at the wiring site** — EvidenceObject.observation_projection_ref is a required field (RT09-INV-1; D8 INV-4) that must reference an admitted RT-08 ObservationRecord. The wiring site is `knowledge-validator.js:_promoteToKnowledge()`, but the ObservationRecord ID is generated inside a `setImmediate()` closure in `claimReality()` and is never returned to the caller. The `knowledge_validation_queue` table has no `obs_record_id` column. No call-chain path from RT-08 to the wiring site exists. IDR-W2-07-001 (Wave 2) previously documented this exact gap and explicitly prohibited fabrication via trace_id.

2. **No EpistemicProtocol registered** — EvidenceObject.interpretation_protocol_ref is required (RT09-INV-3; D6 §4.3 AIR-2). RT09-STATE-02 (EpistemicProtocolRegistry) is empty. No EpistemicProtocol bootstrap infrastructure exists. Unlike KnowledgeClaim (which cannot be bootstrapped — stage-skipping prohibited), EpistemicProtocol is a foundational type with no upstream chain references. A bootstrap is constitutionally feasible per the T3-06/T3-08 pattern with documented limitations.

3. **Domain count implementation gap** — D6 specifies 12 constitutional domains (DOM-000001 through DOM-000012). The system domain-loader implements only 10 (DOM-000011: Reality Architecture and DOM-000012: Theory of Change are absent). EvidenceObject.domain_classification cannot reference these two domains until the implementation gap is resolved. EvidenceObjects for domains 1–10 are not blocked by this gap alone; full 12-domain coverage requires domain-loader update.

All three gaps have clear resolution paths. G-1 requires pipeline modification (threading obsRecordId through the call chain). G-2 requires bootstrapping EpistemicProtocol instances. G-3 requires adding two domain entries to domain-loader.

## Blocking Gap Detail

### Gap G-1 — ObservationRecord ID Not Accessible at Wiring Site

**Constitutional source:** R9-v1.0 RS-07 RT09-OBJ-01: "EvidenceObject must be traceable to an admitted Observation Projection." RT09-INV-1: "Every EvidenceObject must have observation_projection_ref referencing a constitutional ObservationRecord from RT-08."

**EvidenceObject schema enforcement:**
```javascript
observation_projection_ref: { required: true, type: 'string',
  constitutional_source: 'RT09-INV-1; D8 INV-4; R9-v1.0 RS-07',
  description: 'ObservationRecord.record_id from RT-08 that this EvidenceObject derives from.'
}
```

**Pipeline trace:**

| Step | Code | ObservationRecord ID status |
|------|------|-----------------------------|
| claimReality() | `lib/reality/fabric.js` | `obsRecordId` created in setImmediate; returned value is `data.id` (claim ID) — obsRecordId NEVER returned |
| chat.js callers | `src/routes/chat.js` lines ~127, 239, 290, 308 | `submitLesson(reply, { taskId, sourceType: 'observation' })` — no obsRecordId parameter |
| orchestrator.js caller | `agent-system/orchestrator.js` line 886 | `kv.submitLesson(lesson, { traceId, taskId, sourceType: 'auto_reflexion' })` — no obsRecordId parameter |
| submitLesson() | `lib/data/kv.js` | Inserts: validation_id, lesson_text, lesson_source_id, trace_id, task_id, source_type — NO obs_record_id column |
| _promoteToKnowledge() | `lib/intelligence/knowledge-validator.js` | item: { validation_id, lesson_text, lesson_source_id, trace_id, task_id, source_type, confirmations, confidence, evidence, status } — NO ObservationRecord ref |

**IDR-W2-07-001 prior ruling (Wave 2):**
> "Fabrication option considered and rejected: Using trace_id or lesson_source_id as observation_projection_ref would assert a false RT-08 provenance anchor. D8 INV-4 and A1 §6.2 prohibit this. No synthetic value can satisfy RT09-INV-1."

**Resolution path:**
1. Modify `lib/reality/fabric.js` — surface `obsRecordId` from the setImmediate closure (return it alongside the claim ID, or pass it to an event/callback)
2. Modify `lib/data/kv.js` `submitLesson()` — accept optional `obs_record_id` parameter; add `obs_record_id` column to knowledge_validation_queue
3. Modify `src/routes/chat.js` and `agent-system/orchestrator.js` — pass the ObservationRecord ID (obtained from claimReality) to submitLesson()
4. Modify `lib/intelligence/knowledge-validator.js` `_promoteToKnowledge()` — read obs_record_id from item; use as observation_projection_ref in EvidenceObject

This matches the resolution path documented in IDR-W2-07-001 Wave 3 item: "Connect knowledge-validator.js to RT-08 pipeline as D3 epistemic chain consumer."

### Gap G-2 — EpistemicProtocol Registry Empty

**Constitutional source:** RT09-INV-3: "Only registered EpistemicProtocols may be applied to evidence formation." D6 §4.3 AIR-2 obligation. R9-v1.0 RS-10.2: "Registration through constitutionally authorized process (authority undefined — stated limitation)."

**EvidenceObject schema enforcement:**
```javascript
interpretation_protocol_ref: { required: true, type: 'string',
  constitutional_source: 'RT09-INV-3; D6 §4.3 AIR-2; R9-v1.0 RS-10.1',
  description: 'EpistemicProtocol.protocol_id applied during evidence formation.'
}
```

**System state:** RT09-STATE-02 (EpistemicProtocolRegistry) is empty. Zero EpistemicProtocol instances exist.

**Bootstrap feasibility analysis:**

| Type | Required upstream refs | Bootstrap permissible? |
|------|----------------------|----------------------|
| AuthorityGrant (T3-08) | None (foundational) | YES — T3-08 precedent |
| EpistemicProtocol | None (foundational) | YES — same pattern |
| KnowledgeClaim | belief_object_ref, evidence_record_ref, rt09_operation_id | NO — stage-skipping prohibited (D4 KI-007) |

EpistemicProtocol fields (all self-contained): protocol_id, protocol_name, protocol_version, domain_applicability, interpretation_rules. All can be honestly assigned from constitutional design knowledge. The open question on registration authority (RS-12) is a stated limitation, not a prohibition — the same constitutional standing as the T3-08 bootstrap authority limitation L-02.

**Resolution path:**
- Bootstrap at minimum one EpistemicProtocol per constitutional domain (12 total)
- Document: "Registration authority constitutionally undefined per R9-v1.0 RS-12 open question; bootstrap registered under same authority basis as T3-08 bootstrap authority"
- Register in RT09-STATE-02 (EpistemicProtocolRegistry)
- This is a new task within T3-10 scope, analogous to T3-08's authority bootstrap step

### Gap G-3 — Domain-Loader Missing DOM-000011 and DOM-000012

**Constitutional source:** D6-v1.0-canonical.md §2.1 specifies 12 constitutional domains: "Domain identifiers are permanent. They survive domain restructuring. They are never reused."

**Gap detail:**
- D6 canonical: DOM-000001 through DOM-000012 (12 domains)
- System domain-loader: DOM-000001 through DOM-000010 (10 domains)
- Missing: DOM-000011 (Reality Architecture), DOM-000012 (Theory of Change)

**Impact on T3-10:** EvidenceObject.domain_classification must reference a constitutional domain. For EvidenceObjects classified under domains 1–10, this gap is NOT blocking. For EvidenceObjects classified under domains 11–12, this gap is blocking.

**Full-scope impact:** The Wave 3 Authorization Report specifies 12 DUMs (one per domain). Until DOM-000011 and DOM-000012 are in domain-loader, neither T3-10 EvidenceObjects for those domains nor T3-09-DUM DUMs for those domains can be emitted with honest domain_id/domain_classification values.

**Resolution path:**
- Add DOM-000011 (Reality Architecture) and DOM-000012 (Theory of Change) to `lib/registry/domain-loader.js` DOMAIN_MAP
- Add corresponding test coverage in `tests/registry/domain-loader.test.js` (update count assertion from 10 to 12)

## Options for Resolution

### Option A: Full Pipeline Resolution (Recommended)

Complete all three prerequisite resolutions, then wire EvidenceObject at `_promoteToKnowledge()`:

**A.1 — Surface ObservationRecord ID from `claimReality()`**
Modify `lib/reality/fabric.js` to return obsRecordId alongside claim ID. Update callers (chat.js, orchestrator.js) to capture and pass it to submitLesson(). Add `obs_record_id` column to knowledge_validation_queue. Pass through to `_promoteToKnowledge()` via item.

**A.2 — Bootstrap EpistemicProtocol registry**
Register one EpistemicProtocol per constitutional domain in RT09-STATE-02. Document registration authority open question per R9-v1.0 RS-12. Constitutionally honest with stated limitations.

**A.3 — Add DOM-000011 and DOM-000012 to domain-loader**
Extend domain-loader DOMAIN_MAP with Reality Architecture and Theory of Change. Update tests.

**A.4 — Wire EvidenceObject at `_promoteToKnowledge()`**
With prerequisites satisfied: emit constitutional EvidenceObject record at each honest promotion event. Add constitutional tests.

**Constitutional compliance:** Full. No fabrication. observation_projection_ref points to real ObservationRecord. interpretation_protocol_ref points to registered EpistemicProtocol.

Defer T3-10 until the pipeline modification (G-1) is implemented as a separate task. IDR-W2-07-001 (Wave 2) and IDR-W3-10-001 (this document) both remain OPEN, together documenting the same structural gap.
