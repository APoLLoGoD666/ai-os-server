## PART 2 — KERNEL AUTHORITY, SELF-GOVERNANCE, AND OPERATION MANIFEST

### 2.1 Kernel Constitutional Actor Status

The kernel MUST possess a valid ActorProfile (FoundingKernel ActorProfile, SEED-1) established during the Founding Ceremony (Part 13). All kernel actions are attributable to this ActorProfile. The kernel MUST NOT claim constitutional anonymity or exempt itself from attribution.

### 2.2 The Self-Governance Problem and Its Resolution

The kernel enforces constitutional gates. A naive reading of "all operations pass all gates" creates a non-terminating constitutional regress: AccountabilityRecord creation requires kernel processing, which requires an AccountabilityRecord for that processing, which requires kernel processing, without end.

This regress is not resolved by exempting the kernel from accountability. It is resolved by the constitutional distinction between two classes of constitutional operation:

**CLASS A — Actor-Originated Operations**
Operations initiated by constitutional actors (including, when applicable, the kernel as an actor initiating a Class A operation such as a governance challenge). Class A operations MUST pass through the complete six-gate sequence.

**CLASS B — Kernel Manifest Operations**
Operations performed by the kernel in its enforcement capacity as specified in the Kernel Operation Manifest. Class B operations derive their constitutional legitimacy from their structural definition at founding, not from recursive gate evaluation. Class B operations do not undergo recursive Class B processing for their constitutional outputs.

### 2.3 The Kernel Operation Manifest

The Kernel Operation Manifest (hereinafter "the Manifest") is a constitutional object established at FoundingRatification and immutable thereafter. The Manifest is the exhaustive, closed enumeration of every operation type the kernel is constitutionally permitted to perform in its enforcement capacity (Class B).

The Manifest MUST specify, for each kernel operation type:
- the operation name and constitutional purpose
- the triggering condition
- the constitutional outputs produced
- the provenance record generated
- the gate subset (if any) applicable
- the terminating condition that prevents further constitutional event generation from that operation

**The Manifest is finite and closed.** Manifest operation types MUST NOT be added dynamically by the kernel. An operation absent from the Manifest cannot be self-authorized by the kernel. The kernel MUST NOT expand the Manifest through its own authority — Manifest amendment requires founding-level constitutional authority.

At minimum, the Manifest enumerates these Class B operation types, each with its specified termination condition:

| Manifest Operation | Termination Condition |
|---|---|
| RejectionRecord creation | Record written to permanent store; no further Class B processing |
| AccountabilityRecord creation | Record written to permanent store; no further Class B processing |
| Rollback Provenance Record creation | Record written to Provenance Failure Register; no further Class B processing |
| Suspension Notice issuance | Notice delivered and recorded; no further Class B processing |
| CoherenceResolutionEvent (CRE) generation | CRE written to CRE stream; no further Class B processing |
| Constitutional Clarification Request (CCR) generation | CCR registered; no further Class B processing |
| Kernel Failure Log entry | Entry written; no further Class B processing |
| Historical lifecycle transition | Historical record written; no further Class B processing |
| Founding Membership Declaration conversion | Membership record written; no further Class B processing |
| Open Action Register update | Register updated; no further Class B processing |
| Reality Gap entry creation | Entry written; no further Class B processing |

### 2.4 Provenance and Accountability of Manifest Operations

Manifest operations remain provenance-bearing and auditable. Every Class B operation MUST:
- be attributed to the kernel ActorProfile
- generate a provenance record in the kernel operational log (append-only, permanent)
- be distinguishable in audit from Class A operations
- not generate a recursive Class B operation of the same type

Class B operations are exempt from generating AccountabilityRecords or RejectionRecords for their own execution. They are not exempt from kernel attribution, kernel operational log recording, or external constitutional audit.

### 2.5 Reconciliation of KI-032 and KI-033 with KI-036

D4 v1.0 invariants KI-032 and KI-033 stated that the kernel is a constitutional actor subject to the same validation gates. This principle is preserved and refined, not superseded.

**Authoritative reconciled wording:**

The kernel is a constitutional actor whose operations are fully accountable within the constitutional system. Class A operations (actor-originated, including kernel-as-actor operations) undergo the complete six-gate sequence. Class B operations (Manifest operations in the kernel's enforcement capacity) undergo only the gate subset specified in the Manifest for that operation type, generate attribution records in the kernel operational log, and terminate recursion at their constitutionally defined output. The kernel's accountability is preserved through: (a) the immutable FoundingKernel ActorProfile, (b) the append-only kernel operational log, (c) the Manifest's constitutionally fixed definition of kernel operation scope, and (d) external constitutional audit capability.

### 2.6 Kernel Non-Exemption Principle

The kernel MUST NOT:
- perform any enforcement operation not enumerated in the Manifest
- expand the Manifest through its own authority
- claim authority exceeding that established in the FoundingKernel DelegationRecord
- interpret a constitutional silence as self-authorization
- invent a new constitutional rule to resolve an undefined condition (it MUST generate a CCR instead)

When the kernel encounters a constitutional condition for which no Manifest operation and no explicit constitutional rule provides a determinate answer, the kernel MUST generate a CCR and suspend processing of the affected operation stream. The kernel MUST NOT substitute its own judgment for constitutional specification.

## PART 3 — CONSTITUTIONAL OPERATION LIFECYCLE

Every Class A constitutional operation MUST traverse the following ten stages in sequence. No stage may be omitted except as explicitly specified for Manifest operations in Part 2.

### Stage 1 — Intent Registration
The initiating actor presents the operation intent to the kernel. The intent MUST specify: actor identity claim, target object(s), operation type, and epistemic grounding. The kernel assigns a unique operation identifier. This stage is not a gate — it is intake registration.

### Stage 2 — Identity Resolution (Gate 1)
The kernel validates the initiating actor's ActorProfile per Gate 1 (Part 4.1).
**On failure:** RejectionRecord generated; sequence terminates.

### Stage 3 — Object and State Validation (Gate 2)
The kernel validates target existence and operational state per Gate 2 (Part 4.2).
**On failure:** RejectionRecord generated; sequence terminates.

### Stage 4 — Authority Validation (Gate 3)
The kernel validates the actor's authority for the intended operation per Gate 3 (Part 4.3).
**On failure:** RejectionRecord generated; sequence terminates.

### Stage 5 — Epistemic Validation (Gate 4)
The kernel validates epistemic stage eligibility and required priors per Gate 4 (Part 4.4).
**On failure:** RejectionRecord generated; sequence terminates.

### Stage 6 — Constitutive Coherence Validation (Gate 5)
The kernel evaluates constitutive coherence of the proposed change per Gate 5 (Part 4.5). Constitutively invalid operations are rejected before any state change. Conditionally invalid states are not caught here; they are recorded at Stage 10.
**On failure:** RejectionRecord generated; sequence terminates.

### Stage 7 — Temporal and Historical Integrity Validation (Gate 6)
The kernel validates temporal causality and historical integrity per Gate 6 (Part 4.6).
**On failure:** RejectionRecord generated; sequence terminates.

### Stage 8 — Atomic Constitutional Commit
State change and provenance recording are constitutionally indivisible. Both MUST succeed or both MUST be abandoned. The kernel MUST NOT admit a state change without a corresponding provenance record. The kernel MUST NOT create a provenance record claiming an admitted state change that did not occur.

If the atomic commit fails after all six gates have been passed, the kernel MUST generate a Rollback Provenance Record per Part 11.2. The sequence terminates.

### Stage 9 — Post-Commit Provenance Recording
The kernel generates the AccountabilityRecord and completes the provenance chain. Stage 9 is constitutionally inseparable from Stage 8 — together they constitute the full atomic commit. The operation is constitutionally admitted upon successful completion of both Stage 8 and Stage 9.

### Stage 10 — Post-Commit Coherence Evaluation
The kernel evaluates the post-commit coherence impact on the fabric, generating CoherenceResolutionEvents (CREs) per Part 9. CREs do not modify the admitted object. The Mandatory Propagation Window (Part 9.4) begins at Stage 10 initiation.

Stage 10 is not part of the atomic commit. A kernel failure during Stage 10 does not un-commit the Stage 8-9 admission. On recovery, Stage 10 MUST be re-executed from the last CRE stream position for all operations admitted before the failure.

## PART 4 — THE SIX CONSTITUTIONAL GATES

### 4.1 Gate 1 — Identity Resolution

**Constitutional purpose:** Ensure every constitutional operation is attributable to a resolved, active, non-suspended constitutional actor before the operation proceeds.

**Mandatory inputs:** The identity claim presented by the initiating actor.

**Conditions evaluated:**
(a) An ActorProfile exists in the fabric for the claimed identity.
(b) The ActorProfile is in Active lifecycle state (not Historical, Abandoned, or Pending).
(c) The actor has no active OperationalSuspension (Part 10.2).
(d) No unresolved identity challenge blocks the actor's constitutional action.

**Founding Ceremony exception:** Objects and operations within the Founding Ceremony (Part 13) are governed by the Founding Ceremony Protocol. Gate 1 requirements are superseded by the Founding Ceremony Protocol for founding-sequence operations only. This exception expires at FoundingRatification.

**Kernel Manifest exception:** Class B operations are attributed to the FoundingKernel ActorProfile. Gate 1 for Class B verifies only that the FoundingKernel ActorProfile exists and is Active.

**Anonymous operation prohibition:** No constitutional operation may proceed without a resolvable actor identity. If the ActorProfile cannot be resolved, the operation MUST be rejected regardless of any other claim.

**Failure record:** RejectionRecord specifying identity resolution failure and the specific condition not satisfied.

---

### 4.2 Gate 2 — Object and State Validation

**Constitutional purpose:** Ensure every target of a constitutional operation exists in the fabric and is in an operable state for the proposed operation type.

**Mandatory inputs:** Target object reference(s) from Stage 1 intent registration.

**Conditions evaluated:**
(a) Every referenced target object exists in the fabric (possesses a valid StructuralAnchor, has been registered).
(b) Every target object is in a lifecycle state permitting the proposed operation type, per D1 lifecycle model.
(c) Objects under OperationalSuspension are not the target of modification operations but REMAIN readable and retain their existing relationships.
(d) Historical objects are not the target of modification operations but are valid historical reference targets.
(e) Objects in Pending Registration state are not operable as operation principals.

**Relationship creation exception:** For relationship creation operations, Gate 2 validates the existence and operability of the endpoint objects. The relationship being created does not itself exist — Gate 2 does not check the relationship's prior existence, only endpoint operability.

**Superseded endpoint handling:** If a referenced endpoint object is in Historical (superseded) state, Gate 2 evaluates the proposed operation against the Reference Continuity principle (Part 14):
- A historical reference to a superseded object: PERMITTED at Gate 2.
- A new operational dependency on a superseded object: REJECTED at Gate 2.

**ResolutionRecord exception:** A ResolutionRecord operation targeting a suspended object for the purpose of lifting the suspension passes Gate 2, subject to Gate 3 authority validation.

**Failure record:** RejectionRecord specifying object state validation failure, the target object, and the specific condition not satisfied.

---

### 4.3 Gate 3 — Authority Validation

**Constitutional purpose:** Ensure the initiating actor possesses constitutionally valid authority for the proposed operation at the proposed scope before any state change.

**Mandatory inputs:** The actor's authority claims, the proposed operation type, and the target object(s).

**Conditions evaluated:**
(a) At least one AuthorityClaim exists for the actor covering the proposed operation type and target.
(b) Every AuthorityClaim is backed by an unrevoked DelegationRecord.
(c) The DelegationRecord chain is complete and traceable from the ActorProfile to the era's FoundingRatification without cycle.
(d) The claimed scope does not exceed the scope specified in the DelegationRecord chain at any link.
(e) No authority challenge is active and unresolved for the specific AuthorityClaim being invoked.
(f) The actor's autonomy band, as defined in the DelegationRecord, permits the proposed operation without escalation. Operations exceeding the autonomy band MUST escalate before Gate 3 is cleared.

**FoundingRatification exception:** FoundingRatification passes Gate 3 by constitutional declaration. FoundingRatification IS the authority root for the era — its authority cannot be derived from something that exists before it. This exception applies to exactly one object per CivilizationalEra. All other objects MUST have traceable authority chains.

**Kernel Manifest authority:** The kernel's authority for Class B operations derives from the FoundingKernel DelegationRecord established at FoundingRatification. Gate 3 for Class B verifies that the Manifest operation type falls within the kernel's constitutionally delegated enforcement scope.

**Revocation propagation:** If a DelegationRecord in the authority chain has been revoked and the revocation has not yet propagated to all downstream actors, Gate 3 MUST detect the revocation. Operations with chains passing through revoked DelegationRecords are flagged Under Authority Review per Part 7.4.

**Failure record:** RejectionRecord specifying authority validation failure, the specific AuthorityClaim invoked, and the specific condition not satisfied.

---

### 4.4 Gate 4 — Epistemic Validation

**Constitutional purpose:** Ensure every constitutional claim enters the fabric at its correct epistemic stage with all required prior chain objects present.

**Mandatory inputs:** The epistemic stage claimed for the proposed object or state change; references to prior chain objects.

**The D3 epistemic chain** (constitutionally mandatory sequence):
```
Observation → EvidenceRecord → Interpretation → Belief →
KnowledgeClaim → UnderstandingModel → CivilizationalDecision →
CivilizationalAction → ActionEffect → ActionTrace
```

**Conditions evaluated:**
(a) The proposed operation represents a constitutionally valid epistemic stage transition.
(b) All required prior chain objects exist in the fabric and are in Active or Historical state.
(c) For KnowledgeClaims: a valid EvidenceRecord chain traceable to an Observation exists.
(d) For UnderstandingModels: a valid KnowledgeClaim chain exists.
(e) For CivilizationalDecisions: a valid PossibilitySet covering the proposed decision exists and is Active.
(f) For CivilizationalActions: a governing CivilizationalDecision exists and is Active.
(g) For ActionTraces: the governing CivilizationalAction exists and is traceable.
(h) Observation confidence is adjusted to reflect the generating Observer's calibrated reliability. A degraded Observer MUST NOT generate Observations at full confidence — the Observer's UncertaintyDeclaration MUST reflect degraded status.

**Failure record:** RejectionRecord specifying epistemic validation failure, the missing prior chain object or invalid transition, and the specific condition not satisfied.

---

### 4.5 Gate 5 — Constitutive Coherence Validation

**Constitutional purpose:** Prevent constitutively impossible constitutional states from entering the fabric. Gate 5 catches only constitutive invalidity — conditions that cannot be corrected by any subsequent constitutional operation. Conditional invalidity (conditions that could be resolved through future operations) is handled post-commit at Stage 10.

**Mandatory inputs:** The complete proposed operation; the current fabric state for all relevant objects.

**Constitutively prohibited conditions (rejection is mandatory if any apply):**

(a) **SC immutability violation:** Any modification of any field in any StructuralAnchor (SC). SC fields are immutable from the moment of constitutional creation.

(b) **Relationship type incompatibility:** Creation of a relationship with a type incompatible with the ontological categories of its endpoints, per D1.

(c) **Epistemic cycle:** Introduction of a directed cycle in any epistemic chain.

(d) **Provenance cycle:** Introduction of a directed cycle in any provenance chain.

(e) **Deletion:** Deletion of any constitutional object from the fabric. Deletion in any form is constitutively prohibited. Terminal lifecycle transitions move objects to Historical state — they do not delete them.

(f) **Duplicate founding root:** Creation of a second FoundingRatification within the current CivilizationalEra.

(g) **Relationship type mutation:** Modification of an immutable relationship field after origination.

(h) **Isolated node creation:** Creation of a new Active constitutional object without at least one constitutional relationship, except during the Founding Ceremony (below).

**Founding Ceremony exception for (h):** During the Founding Ceremony (Part 13), the isolated-node prohibition is suspended. Seed objects may temporarily lack registered relationships. This exception expires at FoundingRatification, when all seed objects MUST satisfy the relationship requirement.

**Failure record:** RejectionRecord specifying constitutive coherence failure, the specific prohibited condition, and the specific object(s) involved. RejectionRecord is permanent.

---

### 4.6 Gate 6 — Temporal and Historical Integrity Validation

**Constitutional purpose:** Ensure the proposed operation respects causal ordering, temporal consistency, era integrity, and the immutability of the historical record.

**Mandatory inputs:** The proposed operation; its asserted constitutional timestamp; the relevant ChangeRecord and HistoricalAnchor history.

**Conditions evaluated:**
(a) The operation's timestamp is causally consistent with the fabric's established causal ordering for the same causal chain. Effect timestamps MUST NOT precede cause timestamps.
(b) The operation does not backdate historical records to a time inconsistent with established causal history.
(c) The proposed lifecycle transition is permitted by the object's lifecycle state machine. Forbidden transitions are rejected.
(d) The operation's era designation is consistent with the current CivilizationalEra.
(e) ChangeRecords referenced as prior history are present, unaltered, and consistent.
(f) HistoricalAnchor references, where present, are consistent with the proposed operation's temporal claims.

**Failure record:** RejectionRecord specifying temporal integrity failure, the specific temporal or causal violation, and the affected ChangeRecord or HistoricalAnchor reference.

## PART 5 — OBJECT REGISTRATION PROTOCOL

### 5.1 Registration as Constitutional Existence

Every URO (Universal Reality Object, D2) MUST be registered in the fabric before it may participate in any constitutional operation as a principal, target, or relationship endpoint. Registration constitutes constitutional existence. An unregistered object has no constitutional standing.

### 5.2 Registration Sequence

New object registration is a Class A operation traversing all ten stages (Part 3), with the object's complete six-layer URO structure (D2) as the operational payload. All six gates MUST be passed.

Successful registration creates:
- The object's StructuralAnchor (immutable from creation)
- The object's initial SemanticProfile (mutable, version-tracked)
- The object's initial LifecycleRecord (Active state)
- The object's initial CoherenceRegister membership (D2 Layer 5)
- The origination entry in the object's ProvenanceChain (D2 Layer 3)
- The ExistenceAuthorization record (D2 Layer 4)

### 5.3 CoherenceRegister Membership Requirement

Every registered object MUST be a member of at least one of the seven CoherenceRegisters at registration time. The applicable CoherenceRegisters are determined by the object's D1 category. Gate 5 condition (h) enforces this requirement.

The seven CoherenceRegisters are: Ontological, Epistemic, Authority, Value, Temporal, Identity, and Provenance.

**Founding Ceremony exception:** Objects created during the Founding Ceremony hold Founding Membership Declarations in lieu of full RegisterMembership until FoundingRatification converts them atomically. See Part 13.

### 5.4 Layer Completeness Requirement

An object that has not yet had all six D2 layers constitutionally committed is in Pending Registration state. Pending Registration objects:
- are not operable as principals in constitutional operations
- are not valid relationship endpoints for Class A operations
- are exempt from Gate 2 operability validation as targets of their own completion operations

This exception enables atomic multi-layer object construction while preserving the registration requirement.

### 5.5 Supersession

When an object is superseded, the following atomic operation MUST occur:
- The predecessor object transitions to Historical lifecycle state
- The successor object is registered as a new constitutional object
- A SupersessionLink (D2 Layer 6) is established from successor to predecessor
- The HistoricalRecord of the predecessor is created at transition time

Both state transitions are committed atomically. If either fails, both are abandoned. The failed supersession generates a Rollback Provenance Record (Part 11.2).

Historical objects remain permanently in the fabric. They may not be deleted or modified.

## PART 6 — RELATIONSHIP ENFORCEMENT PROTOCOL

### 6.1 Relationships as First-Class Constitutional Objects

Relationships are first-class constitutional objects (D3 RF-A3). Every relationship MUST:
- possess a complete six-layer URO structure (D2)
- be registered through the full ten-stage lifecycle
- be a member of the applicable CoherenceRegisters
- have immutable endpoint references and type designation (D3 GI-9)

### 6.2 Endpoint Validation at Gate 2

Gate 2 for relationship registration validates the existence and operability of endpoint objects. The relationship being registered does not yet exist — Gate 2 checks endpoints, not the relationship's prior existence.

Endpoint objects MUST be in Active lifecycle state for new operational dependency relationships. Reference to Historical endpoints is governed by Part 14 (Reference Continuity).

### 6.3 Type Immutability

The relationship type MUST be compatible with the D1 ontological categories of its endpoints. Evaluated at Gate 5. Type incompatibility is constitutively prohibited. Relationship type MUST NOT be modified after origination.

### 6.4 Relationship Lifecycle

Relationship supersession follows the same protocol as object supersession (Part 5.5). The predecessor relationship is archived to Historical state. A SupersessionLink links the new relationship to its predecessor. The predecessor relationship's endpoint references are preserved unchanged.

### 6.5 Isolated Node Prohibition

No Active constitutional object may exist in the fabric without at least one constitutional relationship (D3 GI-1, D3 RF-A2). Gate 5 condition (h) enforces this. Operational Suspension does not remove this requirement — suspended objects retain their existing relationships.

## PART 7 — AUTHORITY ENFORCEMENT MODEL

### 7.1 Authority Chain Requirement

Every Class A constitutional operation requires a complete, traceable authority chain. The chain MUST:
- originate with the acting actor's ActorProfile
- pass through DelegationRecords in unbroken sequence
- terminate at the era's FoundingRatification
- contain no revoked DelegationRecords
- contain no cycles
- respect scope non-expansion at every delegation step (each delegation MAY narrow, MUST NOT expand)

### 7.2 Scope Non-Expansion Principle

No actor may exercise authority in excess of the scope specified in the DelegationRecord under which authority was granted. This constraint is transitive across the entire chain: the effective scope of any actor's authority is the minimum scope across all DelegationRecords in their chain to FoundingRatification.

### 7.3 Authority Challenges

Any constitutional actor MAY submit an authority challenge identifying a specific AuthorityClaim as constitutionally questionable. During evaluation:
- The challenged AuthorityClaim is flagged
- Operations dependent solely on the challenged claim are placed Under Authority Review
- Operations with unchallenged alternative authority chains MAY proceed

Challenge resolution generates a ResolutionRecord. Open challenges are constitutional obligations visible in the Open Challenge Register.

### 7.4 Authority Revocation and Propagation

When a DelegationRecord is revoked:
(a) The kernel MUST register the revocation and flag it as pending propagation.
(b) All actors whose authority chains pass through the revoked DelegationRecord enter Under Authority Review status.
(c) The Mandatory Propagation Window (Part 9.4) governs the maximum period during which propagation remains constitutionally open.
(d) Operations performed by Under Authority Review actors during the propagation window are admitted and flagged; they are evaluated for constitutional validity after propagation completes.
(e) Authority revocation is NOT retroactive. Operations completed under then-valid authority are constitutionally valid and MUST NOT be retroactively invalidated.
(f) After propagation: actors without a valid alternative authority chain have subsequent operations rejected pending new delegation.

### 7.5 TerminalValue Authority

TerminalValue designations require specific founding-derived authority. No actor may create, modify, or remove TerminalValue objects without explicit TerminalValue authority in their DelegationRecord chain, traceable to FoundingRatification.

### 7.6 Autonomy Bands

Every constitutional actor's DelegationRecord specifies an autonomy band. Operations within the autonomy band proceed at Stage 4 without escalation. Operations exceeding the autonomy band MUST be escalated to the delegating authority before Stage 4 clears.

## PART 8 — DECISION AND ACTION ENFORCEMENT

### 8.1 CivilizationalDecision Requirements

A CivilizationalDecision MUST:
(a) be grounded in an Active PossibilitySet covering the decision domain
(b) select from within the PossibilitySet's enumerated possibilities
(c) have the deciding actor possessing decision authority in the domain, validated at Gate 3

### 8.2 PossibilitySet Constitutional Requirements

A PossibilitySet MUST:
- enumerate constitutionally admissible alternatives for the decision class
- reference the UnderstandingModel(s) grounding the alternatives
- be validated against current KnowledgeClaims in the relevant domain
- expire when the underlying UnderstandingModel is superseded — an expired PossibilitySet MUST NOT ground new Decisions

### 8.3 CivilizationalAction Requirements

A CivilizationalAction MUST:
(a) be governed by an Active CivilizationalDecision covering the action's scope
(b) remain within the governing Decision's scope
(c) have the acting actor possessing execution authority, validated at Gate 3
(d) register the expected ActionEffect before or concurrently with the action's admission

### 8.4 ActionEffect and ActionTrace

Every CivilizationalAction MUST generate at least one expected ActionEffect registration prior to or concurrent with action admission. Every observed ActionEffect MUST generate an ActionTrace back to the originating CivilizationalAction. Untraceable effects MUST generate Reality Gap entries (Part 9.7).

### 8.5 Open Action Visibility

Every CivilizationalAction MUST remain visible in the Open Action Register until:
- an ActionTrace closing the expected ActionEffect is registered, OR
- the action is constitutionally abandoned with a closing AccountabilityRecord

No CivilizationalAction may silently disappear from the Open Action Register. Absence of expected ActionEffect within the Observation Formation Window (OFW) MUST generate a Reality Gap entry. The OFW duration is established constitutionally at founding.

## PART 9 — COHERENCE ENFORCEMENT AND PROPAGATION

### 9.1 Two Constitutional Coherence Modes

D4 recognizes two constitutionally distinct coherence evaluation modes that MUST NOT be conflated:

**Pre-admission constitutive coherence (Gate 5):** Prevents constitutively impossible states from entering the fabric. Operates before any state change. Produces rejection, not conditional records.

**Post-commit conditional coherence (Stage 10):** Evaluates the coherence impact of admitted operations on the surrounding fabric. Produces CoherenceResolutionEvents (CREs). Does not modify admitted objects.

### 9.2 CoherenceResolutionEvents

A CoherenceResolutionEvent (CRE) is a constitutional record produced by Stage 10 evaluation. A CRE MUST specify:
- the admitted operation that triggered the evaluation
- the specific D3 GCR or fabric invariant implicated (GCR-1 through GCR-7)
- all constitutional objects involved
- whether the condition is resolvable, and if so, through what constitutional operation type
- the CoherenceStatus flag to set on affected objects

CREs DO NOT modify admitted objects. A CRE records that an admitted operation creates a conditional coherence condition. The admitted object's constitutional state is fixed by Stage 8-9.

Objects with outstanding CREs are flagged **Under Coherence Evaluation** in their CoherenceStatus (D2 Layer 5). Operations reading such objects MUST acknowledge this flag. The flag MUST remain set until the CRE is resolved or constitutionally closed.

### 9.3 Open CoherenceViolations

All open CoherenceViolations are maintained in the Coherence Violation Register (a constitutional object established at founding). A CoherenceViolation is open until:
- resolved through a subsequent constitutional operation eliminating the violating condition, OR
- constitutionally abandoned with a closing record and AccountabilityRecord

No CoherenceViolation may silently disappear from the register.

### 9.4 Mandatory Propagation Window

The Mandatory Propagation Window (MPW) is the constitutional maximum period within which:
(a) Post-commit coherence evaluation (CRE generation and propagation to all objects in the propagation frontier) MUST complete, and
(b) Authority revocation notifications MUST reach all downstream actors.

The MPW begins at Stage 10 initiation for coherence propagation, or at the moment of DelegationRecord revocation for authority propagation. The MPW duration is established constitutionally at founding (not specified in D4 — duration is a founding decision).

**When propagation exceeds the MPW:**
- The exceedance MUST be registered as a constitutional violation in the Coherence Violation Register
- Affected objects and actors MUST be flagged Unresolved Propagation
- The kernel MUST generate a CCR identifying the propagation failure
- Processing of the affected dependency stream MUST be suspended (Type C Domain Processing Suspension, Part 10.4)

### 9.5 Coherence Propagation Frontier

After an admitted operation, the kernel identifies the propagation frontier: the set of fabric objects and relationships whose CoherenceObligations depend on the admitted object or its CoherenceObligations. The propagation frontier is determined by traversal of CoherenceObligations reverse chains.

The ordering of coherence re-evaluation within the propagation frontier is an architectural decision deferred to D5. The constitutional requirement is: every object in the propagation frontier MUST have its coherence status updated within the MPW.

### 9.6 Interaction with Stage 10 on Recovery

When the kernel recovers from a failure during Stage 10, it MUST re-execute Stage 10 from the last recorded CRE stream position. Stage 10 CRE generation is idempotent with respect to the admitted fabric state — re-execution produces the same CREs because the admitted state is unchanged.

### 9.7 Reality Gap Register

The Reality Gap Register records gaps between expected and observed reality:
- Expected ActionEffects for which no ActionTrace arrived within the OFW
- Expected Observations from configured Observers that did not arrive
- Epistemic chain gaps detected during coherence evaluation

Reality Gap entries are open constitutional conditions. They MUST be visible and tracked until closed through a valid constitutional operation or formally abandoned. No Reality Gap entry may silently expire.

## PART 10 — SUSPENSION, RECOVERY, AND RESOLUTION

### 10.1 Suspension Taxonomy

"Suspension" refers to three constitutionally distinct states. These MUST NOT be conflated. Conflating them constitutes a Type C failure (FM-10). Each type has a distinct trigger, target, effect, and recovery condition.

### 10.2 Type A — Operational Suspension

Operational Suspension is applied to a specific constitutional object or actor when constitutional conditions require that object or actor to cease active participation in constitutional operations.

**Trigger:** OperationalSuspension may be triggered by: (1) constitutive coherence failure requiring the object's immediate isolation, (2) an explicit suspension order under valid authority, (3) authority failure for an actor.

**Target:** A specific constitutional object (any URO) OR a specific ActorProfile.

**Effect on an actor:** The suspended ActorProfile fails Gate 1. The actor cannot initiate constitutional operations while OperationalSuspension is active.

**Effect on an object:** The suspended object fails Gate 2 for modification operations. The object REMAINS readable. Existing relationships to the suspended object remain constitutionally valid and MAY be traversed for read purposes. No new modification relationships may be created targeting the suspended object.

**Scope:** Limited to the specific target identified in the triggering ResolutionRecord. MUST NOT propagate automatically beyond the named target.

**Operations that cease:** Modification operations against the suspended target; initiation of new operations by the suspended actor.

**Operations that continue:** Read access to the target; traversal of existing relationships; historical references to the target; operations by other actors on other objects.

**Recovery condition:** A ResolutionRecord lifting the suspension, issued under authority equal to or exceeding that which imposed it, admitted through the full ten-stage lifecycle.

**Required constitutional record:** ResolutionRecord with explicit suspension type field set to `OPERATIONAL_SUSPENSION`.

---

### 10.3 Type B — Authority Suspension

Authority Suspension prevents a specific actor from exercising authority for new constitutional operations. It does not prevent the actor from being the subject of operations. It does not invalidate historical delegations the actor has previously granted.

**Trigger:** Authority chain revocation or a constitutional finding that an actor's authority exercise was constitutionally irregular.

**Target:** An ActorProfile's authority exercise capacity (not the ActorProfile itself).

**Effect:** The actor's AuthorityClaims fail Gate 3 for new operations. Delegations previously made by the actor under valid authority remain constitutionally valid — operations completed under those delegations are not retroactively invalidated.

**Scope:** New authority exercises only. Does not affect completed operations or the actor's existence as a constitutional object.

**Recovery condition:** A ResolutionRecord restoring authority exercise capacity, or new delegation from a valid superior authority.

**Required constitutional record:** ResolutionRecord with explicit suspension type field set to `AUTHORITY_SUSPENSION`.

---

### 10.4 Type C — Domain Processing Suspension

Domain Processing Suspension is a constitutional control state applied to a specific operation stream or domain when an unresolved CCR prevents constitutional determination of applicable rules for that stream.

**Trigger:** CCR generation when the kernel encounters an undefined constitutional condition affecting an operation stream.

**Target:** The specific operation stream or domain for which the constitutional condition is unresolved. MUST be specified with minimum necessary scope.

**Effect:** Processing of the affected stream is suspended. Unaffected domains and operation streams MUST continue operating. The kernel MUST NOT apply Domain Processing Suspension beyond the minimum scope required by the unresolved CCR.

**Scope:** As narrow as constitutionally possible. The kernel MUST scope the suspension to the specific dependency chain or operation type affected by the unresolved condition.

**Recovery condition:** Resolution of the CCR through the constitutional clarification process, producing a ResolutionRecord.

**Required constitutional record:** CCR with the specific unresolved constitutional question identified; SuspensionNotice identifying the suspended stream.

---

### 10.5 ResolutionRecord Constitutional Requirements

Every ResolutionRecord MUST specify:
- the target object or actor
- the suspension type being addressed (`OPERATIONAL_SUSPENSION`, `AUTHORITY_SUSPENSION`, or domain processing CCR reference)
- the authority under which the resolution is issued (authority chain per Gate 3)
- the constitutional basis for the resolution
- the complete provenance chain for the ResolutionRecord itself

ResolutionRecords are Class A operations subject to the full ten-stage lifecycle.

### 10.6 Suspension and the Isolated Node Rule

Operational Suspension does not exempt an object from the isolated-node prohibition (D3 GI-1). A suspended object retains its existing relationships. The isolated-node prohibition applies to Active objects — if suspension does not change lifecycle state, the object must retain its relationships. Objects whose suspension is implemented as a lifecycle transition to a suspended sub-state retain their relationship membership.

## PART 11 — PROVENANCE, MEMORY, AND HISTORICAL CONTINUITY

### 11.1 The Provenance Guarantee

The kernel MUST enforce both conditions of the following complementary provenance guarantee:

**(a) Completeness:** No admitted state change exists without a corresponding provenance record.

**(b) Accuracy:** No provenance record claims an admitted state change that did not occur.

These conditions are jointly mandatory. Neither relaxes the other. An accurate provenance record that is incomplete violates (a). A complete provenance record that misrepresents a failed commit as admitted violates (b).

### 11.2 The Four Ontological States of a Constitutional Operation

The following four operational states are constitutionally distinct and MUST NOT be conflated:

**REJECTED:** An operation that failed at least one gate check. The fabric state was not changed.
*Constitutional record:* RejectionRecord specifying the gate and condition.

**ADMITTED:** An operation that passed all six gates and completed Stages 8-9.
*Constitutional record:* ChangeRecord + AccountabilityRecord.

**COMMIT FAILED:** An operation that passed all six gates but whose atomic commit (Stage 8-9) failed due to a technical failure.
*Constitutional record:* Rollback Provenance Record (this Part, below).

**LOST:** An operation in progress (Stage 1 through Stage 9) at the time of a kernel failure.
*Constitutional record:* Abandonment entry in the in-progress event log, created on recovery.

### 11.3 Rollback Provenance

When a constitutional operation reaches Stage 8 (all six gates passed) but the atomic commit fails, the kernel MUST generate a Rollback Provenance Record.

The Rollback Provenance Record:
- is stored in the Provenance Failure Register (a founding-era constitutional object)
- is a Manifest operation and does not generate its own Rollback Provenance Record
- is NOT a ChangeRecord and does NOT represent an admitted state change
- is NOT an AccountabilityRecord
- is NOT a RejectionRecord (the operation was not rejected at a gate)

A Rollback Provenance Record MUST contain at minimum:
- the operation identifier from Stage 1
- the complete gate passage record
- the failure point identification
- the kernel attribution (FoundingKernel ActorProfile)
- the constitutional timestamp

The Provenance Failure Register is permanent. Rollback Provenance Records are permanent constitutional records. Historical audit MUST be able to distinguish REJECTED, ADMITTED, COMMIT FAILED, and LOST operations without ambiguity.

### 11.4 ChangeRecord Immutability

All ChangeRecords are constitutionally immutable after creation. No subsequent constitutional operation may alter a ChangeRecord's content, timestamp, or attribution. This immutability is enforced at Gate 5 (SC immutability applied to ChangeRecord identity fields) and Gate 6 (historical integrity).

### 11.5 Historical Inalienability

No constitutional object may be deleted from the fabric (D3 RF-A8). Objects that reach the end of their operational life transition to Historical lifecycle state. Historical objects:
- remain permanently in the fabric
- may not be modified
- may be read and referenced
- may not be the target of modification operations

### 11.6 AccountabilityRecord Requirements

Every admitted constitutional operation MUST generate an AccountabilityRecord specifying:
- the operation identifier
- the admitting actor's ActorProfile reference
- the authority chain summary
- the epistemic grounding
- the constitutional timestamp of admission
- the kernel attribution

AccountabilityRecord creation is a Class B Manifest operation. AccountabilityRecords do not generate their own AccountabilityRecords. This is the constitutional mechanism that terminates the accountability recursion chain.

## PART 12 — CONCURRENCY AND FAILURE RECOVERY

### 12.1 Constitutional Serialization Requirement

No two concurrent operations may modify the same constitutional object simultaneously. The kernel MUST ensure that concurrent modification attempts against the same object are serialized. The observable constitutional requirement: the fabric MUST NOT enter a state where the same object's constitutional state has been simultaneously modified by two uncoordinated operations.

The mechanism by which serialization is achieved is an architectural decision deferred to D5. D4 specifies the constitutional floor: serialization MUST apply at minimum to individual object granularity. Extension to multi-object subgraphs to prevent related conflicts is an architectural decision (D5).

### 12.2 Kernel Failure Recovery

When the kernel fails:
- All in-progress operations (Stage 1 through Stage 9 incomplete) are treated as Lost
- Lost operations MUST be recorded as Abandonment entries in the in-progress event log
- The kernel MUST NOT partially commit or partially recover a lost operation
- The kernel MUST verify a valid Minimum Constitutional State (Part 12.3) before resuming enforcement
- Operations in Stage 10 at the time of failure: the underlying operation was admitted (Stage 8-9 complete); Stage 10 MUST be re-executed from the last CRE stream position on recovery

### 12.3 Minimum Constitutional State (MCS)

The MCS is the minimum information required for the kernel to resume constitutional enforcement. The MCS consists of:

**MCS-1:** The latest valid Fabric Checkpoint (Part 12.4)
**MCS-2:** The complete CRE stream since the latest valid checkpoint, with no gaps
**MCS-3:** All open CoherenceViolations at checkpoint time, updated by the post-checkpoint CRE stream
**MCS-4:** All open CivilizationalAction obligations (Part 8.5)
**MCS-5:** All in-progress operation records from before failure, available for Abandonment processing

The MCS MUST be reconstructable from the permanent constitutional record at any time. On recovery, the kernel MUST verify MCS integrity before resuming Class A operation enforcement.

### 12.4 Fabric Checkpoints and Checkpoint Validity Criteria

A Fabric Checkpoint is a constitutional snapshot of fabric state at a specific constitutional moment. A checkpoint is valid for MCS recovery purposes if and only if it satisfies all four Checkpoint Validity Criteria:

**CVQ-1 — Commitment Completeness:** Every object and relationship included in the checkpoint has completed Stage 8-9 (Atomic Commit + Provenance Recording). No object in Pending Registration state or mid-operation state is included as admitted.

**CVQ-2 — Operation Exclusion:** No in-progress operation (Stage 1 through Stage 7, or Stage 10 incomplete) is represented in the checkpoint as admitted fabric state. In-progress operations at checkpoint time are excluded and recorded in the abandonment log.

**CVQ-3 — CRE Stream Position:** The checkpoint records the CRE stream position as of the checkpoint moment. Objects with outstanding CREs at checkpoint time are included with their Under Coherence Evaluation flags set. The checkpoint does not represent CRE-flagged objects as fully coherence-evaluated.

**CVQ-4 — Serialization State:** The checkpoint records all active serialization obligations at checkpoint time, enabling recovery to correctly serialize resumed operations without creating inadvertent concurrent modification conditions.

A checkpoint is not valid merely because it exists. A checkpoint failing any CVQ MUST be rejected as an MCS basis.

### 12.5 Checkpoint Failure Handling

When the most recent Fabric Checkpoint fails CVQ validation:
(a) The kernel MUST NOT use the invalid checkpoint as MCS basis.
(b) The kernel MUST attempt to verify the next-most-recent checkpoint.
(c) If multiple sequential checkpoints fail, the kernel MUST generate a CCR before resuming Class A enforcement.
(d) Permanent historical evidence (ChangeRecords, AccountabilityRecords) prevails over checkpoint state in any conflict. Checkpoint state MUST NOT override permanent records.
(e) A gap in the CRE or ChangeRecord stream between checkpoint and present MUST be flagged as a constitutional integrity violation requiring investigation before resumption.

### 12.6 Open Action Recovery

On recovery, all open CivilizationalAction obligations MUST be verified against the current constitutional moment. Actions whose OFW expired during the kernel's failure interval MUST have Reality Gap entries generated retroactively. No open CivilizationalAction obligation may be silently lost through a kernel failure.

**(c) Temporary constitutional state:** Suspended Coherence Mode is a temporary constitutional status for founding-era objects. It is not a permanent exemption and expires at FoundingRatification.

## PART 14 — REFERENCE CONTINUITY

### 14.1 The Reference Continuity Principle

Relationships reference specific constitutional versions of their endpoint objects. When an endpoint object is superseded, the relationship retains its reference to the version that existed at the time of the relationship's creation. That reference is constitutionally valid and MUST NOT be silently rewritten.

Reference Continuity preserves historical inalienability at the relationship level: the historical record reflects what was related at the time, not what is currently related.

### 14.2 Historical Reference vs. Operational Dependency

Two constitutionally distinct reference types require distinct treatment:

**Historical Reference:** A relationship whose endpoint object has transitioned to Historical state. The relationship continues to reference the specific historical version. This reference is constitutionally valid. It documents a past constitutional state. Historical references MAY be created or retained.

**Operational Dependency:** A relationship through which an Active constitutional function depends on an Active endpoint object. If the endpoint is superseded, the operational dependency requires evaluation — continued reliance on the Historical version may no longer be constitutionally adequate.

Gate 2 distinguishes these cases. New relationships proposed after an endpoint's supersession must be evaluated: are they historical references to a past state, or new operational dependencies requiring an Active endpoint? New operational dependencies targeting superseded objects fail Gate 2.

### 14.3 Successor Resolution

When a superseded endpoint creates an ambiguous operational dependency that requires successor resolution:
(a) The kernel MUST flag the dependency as requiring successor resolution.
(b) Successor resolution is a constitutional operation — it MUST be performed explicitly and MUST NOT happen silently or automatically.
(c) Successor resolution creates a new relationship referencing the successor object, linked by SupersessionLink to the predecessor relationship.
(d) The predecessor relationship is preserved unchanged (Historical Inalienability, Part 11.5).
(e) When no valid successor exists: the operational dependency is flagged as an open constitutional resolution obligation; processing depending on the relationship is flagged as constitutionally uncertain; a CCR MUST be generated if the ambiguity exceeds resolution authority.

### 14.4 CoherenceObligations and Historical Endpoints

CoherenceObligations that reference superseded objects are evaluated against the predecessor's historical state. If a CoherenceObligation requires an Active endpoint and the endpoint is Historical, Stage 10 evaluation generates a CRE identifying the CoherenceObligation as conditionally impaired. Successor resolution (Part 14.3) is the constitutional path to closing the CRE.

### 14.5 Gate Treatment of Superseded Endpoints

**Gate 2 for superseded endpoints:**
- Historical reference operations: PASS Gate 2
- New operational dependency on superseded object: FAIL Gate 2

**Gate 5 for superseded endpoints:**
- Creating a relationship documenting a historical reference: PERMITTED
- Creating a new operational dependency on a superseded object: PROHIBITED (constitutively)

*Enforcement: Part 14, Gate 2, Gate 5. Failure: Silent historical rewrite — constitutional integrity violation; new operational dependency on superseded object — RejectionRecord.*

**KI-042 — Checkpoint Validity Criteria**
A Fabric Checkpoint is valid for MCS recovery purposes if and only if it satisfies all four Checkpoint Validity Criteria simultaneously: CVQ-1 Commitment Completeness (all included objects past Stage 8-9), CVQ-2 Operation Exclusion (no in-progress operations represented as admitted), CVQ-3 CRE Stream Position (CRE position recorded; Under Coherence Evaluation flags preserved), CVQ-4 Serialization State (active serialization obligations recorded). A checkpoint failing any CVQ MUST NOT be used as MCS basis. Permanent constitutional records (ChangeRecords, AccountabilityRecords) prevail over checkpoint state in any conflict. A checkpoint does not supersede the permanent record.
*Enforcement: Part 12.4, Part 12.5. Failure: Invalid checkpoint used — constitutional integrity violation; FM-12.*

## PART 16 — CONSTITUTIONAL FAILURE MODE REGISTER

This register defines the constitutionally specified failure modes recognized by D4. Detection, consequence, and recovery path are specified for each mode.

---

**FM-1 — Identity Failure**
*Condition:* Actor identity cannot be resolved at Gate 1 (ActorProfile absent, inactive, or OperationallySuspended).
*Classification:* Pre-admission.
*Constitutional consequence:* Operation rejected.
*Record:* RejectionRecord specifying identity resolution failure.
*Suspension triggered:* None automatically.
*Recovery path:* Actor must have ActorProfile established or restored through valid constitutional operation, or suspension lifted.

---

**FM-2 — Object State Failure**
*Condition:* Target object is absent from the fabric, not operable for the proposed operation type, or in a prohibited lifecycle state.
*Classification:* Pre-admission.
*Constitutional consequence:* Operation rejected.
*Record:* RejectionRecord specifying object state failure and target.
*Suspension triggered:* None automatically.
*Recovery path:* Object state must be corrected through valid constitutional operations or object re-registered.

---

**FM-3 — Authority Chain Failure**
*Condition:* Actor lacks valid authority for the proposed operation; chain is incomplete, cyclic, out-of-scope, or traverses a revoked DelegationRecord.
*Classification:* Pre-admission.
*Constitutional consequence:* Operation rejected.
*Record:* RejectionRecord specifying authority chain failure. Active challenges generate Under Authority Review flag.
*Suspension triggered:* None automatically. Revocation propagation triggers FM-9.
*Recovery path:* Valid DelegationRecord must be established or existing chain verified through constitutional challenge resolution.

---

**FM-4 — Epistemic Chain Failure**
*Condition:* The proposed epistemic operation lacks required prior chain objects, attempts an invalid stage transition, references an expired PossibilitySet, or a degraded Observer presents full-confidence Observations.
*Classification:* Pre-admission.
*Constitutional consequence:* Operation rejected.
*Record:* RejectionRecord specifying epistemic validation failure and missing requirement.
*Suspension triggered:* None automatically.
*Recovery path:* Required prior chain objects must be established before re-attempting.

---

**FM-5 — Constitutive Coherence Failure**
*Condition:* The proposed operation would introduce a constitutively impossible state (SC mutation, epistemic cycle, provenance cycle, deletion attempt, duplicate FoundingRatification, relationship type mutation, or new isolated node outside founding).
*Classification:* Pre-admission. Constitutively prohibited — irreparable.
*Constitutional consequence:* Operation rejected. The proposed operation cannot be modified to become constitutionally valid for the specific prohibited condition — it must be abandoned.
*Record:* RejectionRecord specifying the prohibited condition and object(s).
*Suspension triggered:* None (the violation never entered the fabric).
*Recovery path:* None for the rejected operation. The prohibited condition class is permanently blocked.

---

**FM-6 — Temporal Integrity Failure**
*Condition:* The proposed operation violates causal ordering, introduces an impossible timeline, attempts to backdate historical records, specifies a forbidden lifecycle transition, or is inconsistent with the current CivilizationalEra.
*Classification:* Pre-admission.
*Constitutional consequence:* Operation rejected.
*Record:* RejectionRecord specifying temporal violation and affected records.
*Suspension triggered:* None automatically.
*Recovery path:* Temporal claims must conform to the established causal record.

---

**FM-7 — Post-Commit Coherence Violation**
*Condition:* An admitted operation creates a conditional coherence condition with respect to D3 GCR-1 through GCR-7.
*Classification:* Post-commit. The operation is admitted; the condition is conditional and potentially resolvable.
*Constitutional consequence:* CRE generated. Affected objects flagged Under Coherence Evaluation. Open CoherenceViolation registered in the Coherence Violation Register.
*Record:* CRE specifying the specific GCR implicated and objects involved.
*Suspension triggered:* None automatically from a single CRE. MPW exceedance triggers FM-9.
*Recovery path:* A subsequent constitutional operation eliminating the violating condition, or constitutionally closed abandonment with AccountabilityRecord.

---

**FM-8 — Observer Degradation**
*Condition:* An Observer's reliability falls below the calibration threshold. Expected Observations fail to arrive within the OFW.
*Classification:* Post-event detection.
*Constitutional consequence:* Reality Gap entry generated. Observer reliability downgraded in calibration record. Subsequent Observations from degraded Observer carry adjusted confidence, enforced at Gate 4.
*Record:* Reality Gap entry; Observer calibration record update.
*Suspension triggered:* None automatically unless Observer degradation is assessed as constitutively disabling for epistemic chain requirements.
*Recovery path:* Observer recalibration and certification.

---

**FM-9 — Propagation Window Exceeded**
*Condition:* Post-commit CRE propagation or authority revocation notification exceeds the Mandatory Propagation Window.
*Classification:* Post-admission.
*Constitutional consequence:* Exceedance registered as constitutional violation. Affected objects/actors flagged Unresolved Propagation. CCR generated. Domain Processing Suspension (Type C) applied to affected dependency stream.
*Record:* Constitutional violation record; CCR; SuspensionNotice.
*Suspension triggered:* Type C — affected operation stream.
*Recovery path:* CCR resolution establishing propagation completion or new authority delegation.

---

**FM-10 — Constitutional Clarification Required**
*Condition:* The kernel encounters a constitutional condition for which no Manifest operation and no explicit constitutional rule provides a determinate answer.
*Classification:* Pre-admission (detected during evaluation of an operation).
*Constitutional consequence:* CCR generated. Domain Processing Suspension (Type C) applied to the affected operation stream. Processing of unaffected streams MUST continue.
*Record:* CCR with specific unresolved question; SuspensionNotice.
*Suspension triggered:* Type C — minimum-scope.
*Recovery path:* Constitutional clarification process concludes; CCR resolved.

---

**FM-11 — Unauthorized Kernel Manifest Expansion**
*Condition:* The kernel executes a Manifest operation not enumerated in the constitutionally established Manifest, or attempts to add an operation type to the Manifest through its own authority.
*Classification:* Constitutional integrity violation.
*Constitutional consequence:* The unauthorized operation is treated as constitutionally illegitimate. Constitutional integrity violation registered. Kernel Failure Log entry. CCR generated.
*Record:* Kernel Failure Log entry; CCR; constitutional integrity violation record.
*Suspension triggered:* Type C — affected operation stream, pending CCR resolution.
*Recovery path:* Founding authority review of whether the Manifest requires amendment (which requires founding-level authority, not kernel authority).

---

**FM-12 — Invalid Checkpoint Accepted as MCS Basis**
*Condition:* A Fabric Checkpoint that fails one or more Checkpoint Validity Criteria is used or would be used as the MCS recovery basis.
*Classification:* Recovery error — constitutional integrity violation.
*Constitutional consequence:* Constitutional integrity violation registered. CCR generated. Recovery halted pending valid MCS establishment.
*Record:* Constitutional integrity violation record; CCR; failed CVQ identification.
*Suspension triggered:* Kernel recovery suspended until valid MCS established.
*Recovery path:* Valid checkpoint identified, or MCS reconstructed from permanent historical records (ChangeRecords, AccountabilityRecords). Permanent records prevail over checkpoint state.

## PART 17 — D4 CONSTITUTIONAL BOUNDARY CERTIFICATION

This certification establishes that every implementation-adjacent term in D4 v2.0 specifies a constitutional property rather than a specific engineering mechanism.

| Term | Constitutional Property Specified | Why Not Implementation |
|------|----------------------------------|------------------------|
| Atomic Constitutional Commit | State change and provenance are constitutionally indivisible; both succeed or both are abandoned | The mechanism (database transaction, event sourcing, write-ahead log, etc.) is an architectural choice that may satisfy the property in multiple ways |
| Sequential Constitutional Obligation / Serialization | The fabric must never enter a state where the same object's constitutional state is simultaneously modified by two uncoordinated operations | Lock, queue, actor model, event ordering — any mechanism guaranteeing the observable property is constitutionally equivalent |
| Kernel Operation Manifest | A constitutionally immutable, founding-established, finite enumeration of kernel enforcement operation types | The data structure, storage, and lookup mechanism are architectural |
| Mandatory Propagation Window | CRE propagation and authority revocation notification MUST complete within a constitutional maximum period | The propagation algorithm, ordering, and worker mechanism are architectural; only the bounding property is constitutional |
| Fabric Checkpoint | A constitutional snapshot satisfying CVQ-1 through CVQ-4 | Checkpointing may be achieved by snapshot, event sourcing, content-addressed storage, or any equivalent mechanism |
| CoherenceRegister | A constitutional category-membership structure; every URO belongs to at least one | The register's data structure, schema, and query mechanism are architectural |
| Reference Continuity | Historical references to superseded objects are valid; new operational dependencies on superseded objects are prohibited; historical relationships must not be silently rewritten | The mechanism for tracking predecessor/successor relationships is architectural |
| Rollback Provenance Record | A constitutional evidence record of a commit-failed operation that does not claim an admitted state change | Structure is partially constrained by required fields (Part 11.3); storage mechanism is architectural |
| Open Action Register | CivilizationalActions remain constitutionally visible until closed or abandoned | Register implementation (table, log, materialized view, etc.) is architectural |
| Reality Gap Register | Reality gaps are constitutionally recorded and visible | Register implementation is architectural |
| Provenance Failure Register | Rollback Provenance Records are stored permanently | Register implementation is architectural |
| Coherence Violation Register | Open CoherenceViolations are constitutionally visible and tracked | Register implementation is architectural |

**CERTIFICATION STATEMENT:** D4 v2.0 contains no source code, no programming language constructs, no database schema definitions, no SQL, no API signatures, no HTTP routes, no specific infrastructure specifications, and no references to specific implementation vendors or technologies. Every implementation-adjacent term above specifies a constitutional property that is satisfiable by multiple materially different implementations. D4 v2.0 passes the boundary test at every term examined.
