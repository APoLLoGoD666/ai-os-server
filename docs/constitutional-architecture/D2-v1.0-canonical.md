## PREAMBLE

D2 answers one question: *What is the minimum constitutional structure that every APEX representational object must possess to remain a valid participant in the civilization's reality-tracking function?*

D2 does not describe implementation. It does not describe database schemas, class hierarchies, or API contracts. It describes the constitutional architecture — the set of invariants that every object must satisfy to be recognized as a legitimate APEX object at all.

The Universal Reality Object (URO) is not itself instantiated. It is the constitutional template from which every concrete APEX category derives its constitutional legitimacy. An object that cannot demonstrate conformance to the URO is not an APEX object; it is a data artifact without constitutional standing.

## PART 1: UNIVERSAL REALITY OBJECT — DEFINITION

### 1.1 Statement

The **Universal Reality Object (URO)** is the minimum constitutional structure that any representational object must possess to participate in the APEX civilization's reality-tracking, epistemic, authority, and coherence systems.

The URO is defined by three axioms:

**URO-A1 — Constitutional Completeness:**
Every APEX object must be constitutionally complete. Constitutional completeness requires the presence of all three identity aspects (StructuralAnchor, SemanticProfile, ReferentialLink), an unbroken provenance chain traceable to a FoundingRatification, an epistemic posture appropriate to its category, and coherence register membership for all applicable registers.

**URO-A2 — Constitutional Legibility:**
Every APEX object must be constitutionally legible. Constitutional legibility means that every property of the object that bears on reality-tracking, epistemic integrity, authority traceability, or coherence evaluation is expressed in terms recognizable to the constitutional framework — not opaque, not implementation-internal, not privately defined.

**URO-A3 — Constitutional Continuity:**
Every APEX object must maintain constitutional continuity across all state changes. No state change may break constitutional completeness or legibility. If a state change would break either, the change must be prohibited or converted into a Supersession that creates a new constitutionally-compliant successor object.

### 1.2 Scope

The URO governs every object belonging to any D0 category. This includes:
- All entity types (Entity and all specializations)
- All epistemic objects (Observation through ActionEffect)
- All coherence objects (CoherenceRelation, CoherenceViolation, ResolutionRecord)
- All value objects (TerminalValue, InstrumentalValue, ValueDerivation)
- All authority objects (FoundingRatification through AccountabilityRecord)
- All historical objects (HistoricalRecord through ProvenanceChain)
- All D1.1 objects (ActorProfile, PossibilitySet, PossibleAction, AbstractConcept)

**Not governed by the URO:** RealitySegments, ExternalStates, and Occurrences — these belong to external reality and are not APEX representational objects. They are referenced by APEX objects but not constituted by the URO. Observations are the boundary: they are the first APEX objects in the epistemic chain, and they are fully URO-governed.

## PART 2: UNIVERSAL OBJECT STRUCTURE

The URO is constituted by six **Constitutional Layers**. Each layer is mandatory for all APEX objects. Layers are non-collapsible — no layer may be merged into another, eliminated, or made optional.

---

### Layer 1 — IDENTITY LAYER

**Purpose:** Establish and maintain the three-aspect identity of the object.

**Components:**

**L1.1 — StructuralAnchor (SC)**

The SC is the persistent, immutable individuating core of the object. It is a PersistenceInvariant established at origination and never modified.

Structure:
```
StructuralAnchor {
    OriginalContext {
        InstantiationOccasion    : TemporalPosition       [1..1, immutable]
        ScopeDefinition          : ScopedDescription      [1..1, immutable]
        CategoryMembership       : D0-Category            [1..1, immutable]
        CivilizationalEra        : EraDesignation         [1..1, immutable]
    }
}
```

Constitutional constraint: No property within SC may ever be modified after origination. If any would-be modification is necessary, it constitutes a Supersession, not an update.

SC is the identity of the object. Without SC, the object has no individuation and cannot be tracked across time.

**L1.2 — SemanticProfile (SM)**

The SM is the mutable meaning-bearing component of the object. It carries what the object currently represents, asserts, or characterizes. SM may change across the object's lifecycle; each significant change generates a ChangeRecord.

Structure:
```
SemanticProfile {
    CurrentContent           : PropositionalContent       [1..1, mutable]
    ConfidenceLevel          : ConfidenceLevel            [1..1, mutable]
    EpistemicStatus          : Category-specific status   [1..1, mutable]
    LastUpdatedAt            : TemporalPosition           [1..1, mutable]
    UpdateHistory            : [ChangeRecord]             [0..*, append-only]
}
```

Constitutional constraint: SM changes must preserve the SC. SM changes are not identity changes; they are semantic evolution within the same identity. If the SM change would require a new SC (new CategoryMembership, new ScopeDefinition), the result is a new object with a Supersession linking it to the prior.

**L1.3 — ReferentialLink (RL)**

The RL is the directional pointer from the APEX object toward what it represents, refers to, or is about. RL is structurally independent from both SC and SM.

Structure:
```
ReferentialLink {
    ReferentType     : { RealitySegment | ExternalState | Occurrence | Entity | AbstractConcept | None }
    ReferentHandle   : ExternalReference | EntityReference | null
    GroundingQuality : GroundingQuality
    GroundingBasis   : EvidenceRecord[]   [0..*]
}
```

Constitutional constraint: Every APEX object must have an RL, even if its ReferentType is None (in which case it is explicitly self-referential or purely relational). The RL cannot be empty by omission — absence of reference must be positively declared.

### Layer 2 — EPISTEMIC POSTURE LAYER

**Purpose:** Declare the object's position in the epistemic chain and the epistemic constraints it must satisfy.

**Components:**

**L2.1 — ChainPosition**

```
ChainPosition {
    Stage          : EpistemicStage    [1..1, immutable-at-origination]
    PriorStage     : EpistemicStage | null
    RequiredPriors : [EpistemicStage]
}
```

EpistemicStage values (ordered): Observation → EvidenceRecord → Interpretation → Belief → KnowledgeClaim → UnderstandingModel → CivilizationalDecision → CivilizationalAction → ActionEffect → ActionTrace

Constitutional constraint: No object may claim a ChainPosition without satisfying all RequiredPriors. A KnowledgeClaim cannot exist without a traceable chain reaching back to at least one Observation.

**L2.2 — EpistemicGrounding**

```
EpistemicGrounding {
    SupportingEvidence    : [EvidenceRecord]         [0..*]
    GroundingCompleteness : EvidenceStrength         [1..1]
    ValidationStatus      : ValidationStatus         [1..1]
    JustificationPath     : [EpistemicStage-ref]     [0..*]
}
```

For objects at ChainPosition Stage ≥ KnowledgeClaim: SupportingEvidence must be non-empty; ValidationStatus must not be {unvalidated}; JustificationPath must be traceable without gaps.

**L2.3 — UncertaintyDeclaration**

Every APEX object must carry an explicit uncertainty declaration. No object is permitted to be epistemically silent about its confidence.

```
UncertaintyDeclaration {
    ConfidenceLevel          : ConfidenceLevel      [1..1]
    ConfidenceBasis          : ScopedDescription    [1..1]
    GapsAcknowledged         : [ScopedDescription]  [0..*]
    ConflictingEvidence      : [EvidenceRecord]     [0..*]
}
```

Constitutional constraint: A ConfidenceLevel of 1.0 (certainty) is only permissible for objects that are constitutively true by definition (e.g., FoundingRatification — its authority derives from the act of ratification, not from external validation). All empirical objects must carry ConfidenceLevel < 1.0 unless constitutively grounded.

### Layer 3 — PROVENANCE LAYER

**Purpose:** Maintain the unbroken causal record from origination to present state.

**Components:**

**L3.1 — OriginationRecord**

```
OriginationRecord {
    OriginatingActor       : ActorProfile-ref        [1..1]
    OriginatingAuthority   : AuthorityClaim-ref      [1..1]
    OriginatingOccasion    : Occurrence-ref          [1..1]
    OriginatingRationale   : PropositionalContent    [1..1]
}
```

Constitutional constraint: Every APEX object must record how it came into existence. "How" includes who originated it, under what authority, on what occasion, and for what reason. These cannot be retroactively modified.

**L3.2 — ProvenanceChain**

```
ProvenanceChain {
    Links       : [ProvenanceLink]   [1..*, append-only]
    IsComplete  : boolean
    IsVerified  : boolean
}

ProvenanceLink {
    FromObject      : URO-ref
    ToObject        : URO-ref
    RelationType    : ProvenanceRelationType
    AtOccasion      : Occurrence-ref
    AuthorizedBy    : AuthorityClaim-ref
}
```

ProvenanceRelationType values: { derived-from | generated-by | validated-by | superseded-by | recorded-in | attributed-to }

Constitutional constraint: For KnowledgeClaims and UnderstandingModels, IsComplete must be true. For all other objects, IsComplete is advisory — but no link in the chain may be fabricated or backdated.

**L3.3 — ModificationHistory**

```
ModificationHistory {
    Records    : [ChangeRecord]    [0..*, append-only]
}
```

Every change to any Layer of the URO that is not the initial origination generates a ChangeRecord. ChangeRecords are append-only. No ChangeRecord may be deleted or modified after creation.

### Layer 4 — AUTHORITY LAYER

**Purpose:** Establish the legitimacy of the object's existence and any authority it exercises or claims.

**Components:**

**L4.1 — ExistenceAuthorization**

```
ExistenceAuthorization {
    AuthorizingClaim      : AuthorityClaim-ref      [1..1]
    AuthorityChain        : [AuthorityClaim-ref]    [1..*, ordered]
    TerminatesAt          : FoundingRatification-ref [1..1]
    CompetenceRequired    : [CompetenceDemonstration-ref] [0..*]
}
```

Constitutional constraint: Every APEX object must be authorized to exist. Authorization traces through a chain of AuthorityClaims to a single FoundingRatification. No object may exist without this chain. An object whose chain is broken is in an invalid state — it must either have its chain repaired or be superseded.

**L4.2 — AuthorityExercised** *(present only for objects that exercise authority)*

```
AuthorityExercised {
    ClaimedAuthority      : AuthorityClaim-ref      [1..1]
    DerivedFrom           : AuthoritySource-ref     [1..1]
    AccountableRecord     : AccountabilityRecord-ref [1..1]
}
```

For objects that do not exercise authority (e.g., EvidenceRecord, Observation), this component is absent. Absence is not a defect — it means the object makes no authority claims, which is constitutionally valid.

**L4.3 — AccountabilityBurden**

```
AccountabilityBurden {
    AffectedEntities      : [Entity-ref]   [0..*]
    ReviewPeriod          : TemporalPosition | null
    OpenChallenges        : [AuthorityChallenge-ref] [0..*]
}
```

### Layer 5 — COHERENCE LAYER

**Purpose:** Track the object's membership in and obligations to the seven CoherenceRegisters.

**Components:**

**L5.1 — RegisterMembership**

```
RegisterMembership {
    Registers       : [CoherenceRegister-ref]    [1..7]
    PrimaryRegister : CoherenceRegister-ref      [1..1]
}
```

All APEX objects participate in at least one of the seven CoherenceRegisters. Every object must declare its PrimaryRegister — the register that most directly governs its coherence obligations.

The seven CoherenceRegisters (from D1):
1. Ontological Register (structural category consistency)
2. Epistemic Register (epistemic chain integrity)
3. Authority Register (authority chain validity)
4. Value Register (value alignment)
5. Temporal Register (temporal ordering consistency)
6. Identity Register (three-aspect identity consistency)
7. Provenance Register (provenance chain completeness)

**L5.2 — CoherenceStatus**

```
CoherenceStatus {
    PerRegister    : Map<CoherenceRegister, {Consistent | Violated | Pending}>
    ActiveViolations : [CoherenceViolation-ref]   [0..*]
    PendingResolutions : [ResolutionRecord-ref]   [0..*]
}
```

Constitutional constraint: An APEX object with an unresolved CoherenceViolation in the Ontological or Identity Registers is constitutionally suspended — it may not be referenced by other objects until the violation is resolved.

**L5.3 — CoherenceObligations**

```
CoherenceObligations {
    DependsCoherentlyOn   : [URO-ref]   [0..*]
    MustRemainCoherentWith : [URO-ref]  [0..*]
}
```

When an object in DependsCoherentlyOn or MustRemainCoherentWith changes its coherence status, this object's CoherenceStatus must be re-evaluated.

### Layer 6 — HISTORICAL CONTINUITY LAYER

**Purpose:** Ensure the object's past is preserved, its future transitions are recorded, and its participation in the non-erasure commitment is structurally enforced.

**Components:**

**L6.1 — LifecycleRecord**

```
LifecycleRecord {
    CurrentState    : LifecycleState     [1..1]
    ValidFrom       : TemporalPosition   [1..1]
    ValidUntil      : TemporalPosition | null
    Transitions     : [LifecycleTransition]  [0..*, append-only]
}

LifecycleTransition {
    FromState       : LifecycleState
    ToState         : LifecycleState
    AtOccasion      : Occurrence-ref
    AuthorizedBy    : AuthorityClaim-ref
    Rationale       : PropositionalContent
}
```

Universal LifecycleState values: { active | superseded | historical | archived }

Constitutional constraint: The only terminal states are {superseded, historical, archived}. There is no {deleted} state. An object may not cease to exist; it may only cease to be active. Every transition to a terminal state requires an AuthorityClaim.

**L6.2 — SupersessionLink** *(present only when state = superseded)*

```
SupersessionLink {
    SuccessorObject      : URO-ref          [1..1]
    SupersessionOccasion : Occurrence-ref   [1..1]
    SupersessionRationale : PropositionalContent [1..1]
}
```

A superseded object retains all its Layers. The SupersessionLink simply points to its legitimate successor. The predecessor remains fully readable as HistoricalRecord.

**L6.3 — HistoricalAnchor**

Every APEX object, when it transitions to {historical}, must generate a HistoricalRecord that captures the complete state of all six Layers at the moment of transition. The HistoricalRecord is itself a URO-governed object and must be constitutionally complete.

## PART 3: OBJECT LIFECYCLE MODEL

### 3.1 Universal Lifecycle

All APEX objects follow a single universal lifecycle model:

```
[Origination] → [Active] → [Superseded] → [Historical]
                          ↘ [Archived]
```

**Origination:** All six Layers must be populated before the object transitions to Active. An object that has not completed all six Layers is in a pre-constitutional state and is not a valid APEX object. Pre-constitutional objects may not be referenced.

**Active:** The object participates fully in the civilization's epistemic, authority, and coherence systems. SM and CoherenceStatus may change. SC, OriginationRecord, and all append-only fields may not change.

**Superseded:** The object has been legitimately replaced by a successor. All Layers are frozen. The SupersessionLink is established. The object remains fully readable. Active references to this object should be updated to reference the successor; historical references (e.g., within ChangeRecords) should be preserved as-is.

**Historical:** The object has permanently exited active participation. A HistoricalAnchor has been generated. The object may not be reactivated.

**Archived:** A variant of Historical used for objects that remain valid but are moved to reduced-access storage. Constitutional integrity is maintained; operational accessibility may differ. Archived objects are not deleted.

### 3.2 Forbidden Transitions

| From | To | Reason Forbidden |
|------|----|-----------------|
| Any | Deleted | Non-erasure axiom (A-S6) |
| Historical | Active | Non-reversibility |
| Superseded | Active | Non-reversibility |
| Active | Origination | Non-reversibility |
| Historical | Superseded | Sequence violation |

### 3.3 Transition Authority Requirements

| Transition | Required Authority |
|------------|-------------------|
| Origination → Active | CompetenceDemonstration for relevant domain |
| Active → Superseded | AuthorityClaim of scope ≥ object's scope |
| Active → Archived | AuthorityClaim of scope ≥ object's scope |
| Superseded → Historical | Registry Kernel authority |
| Active → Historical (direct, exceptional) | FoundingRatification-level authority only |

## PART 4: UNIVERSAL RELATIONSHIP MODEL

All relationships between APEX objects are themselves URO-governed. A relationship is not a simple pointer — it is a first-class APEX object that carries all six Layers.

### 4.1 Relationship as URO

```
URO-Relationship {
    // All six URO Layers apply
    // Plus relationship-specific fields:
    SourceObject       : URO-ref    [1..1, immutable]
    TargetObject       : URO-ref    [1..1, immutable]
    RelationshipType   : D0-RelationshipType  [1..1, immutable]
    RelationshipScope  : ScopedDescription    [1..1]
    DirectionMeaning   : PropositionalContent [1..1]
}
```

Constitutional implication: Deleting a relationship is not permitted. A relationship becomes Superseded when it is no longer valid. The record that it once held is preserved as HistoricalRecord.

### 4.2 Relationship Type Hierarchy

All D0-specified relationships are constitutional relationship types. D2 introduces a universal supertype from which all constitutional relationships derive:

```
URO-RelationshipType
├── EpistemicRelationship    { grounds | derives-from | validates | interprets | contradicts }
├── ProvenanceRelationship   { derived-from | generated-by | validated-by | superseded-by | recorded-in | attributed-to }
├── AuthorityRelationship    { authorized-by | delegates-to | accountable-to | challenged-by }
├── IdentityRelationship     { same-entity-as | specializes | is-aspect-of }
├── CoherenceRelationship    { consistent-with | violates | resolves }
├── ValueRelationship        { serves-value | derives-value-from | conflicts-with-value }
└── HistoricalRelationship   { supersedes | records | continues }
```

### 4.3 Relationship Cardinality Constraints

Inherited from D1. D2 adds one universal constraint:

**D2-RC-01:** No APEX object may have zero outgoing relationships. Every object must be related to at least one other APEX object — if nothing else, to its own OriginatingOccasion and its own AuthorityClaim. Isolated objects are constitutionally incomplete.

### 4.4 Relationship Coherence

When a relationship transitions to Superseded, it does not automatically supersede either endpoint. The endpoints must independently evaluate their CoherenceStatus. If the lost relationship causes a coherence violation in either endpoint, that endpoint enters a CoherenceViolation state that must be resolved.

## PART 5: INHERITANCE AND SPECIALIZATION MODEL

### 5.1 Principle of Constitutional Inheritance

Every D0 category specializes the URO. Specialization is additive: a specialized object carries all six URO Layers plus category-specific fields. Specialization never removes or weakens a URO Layer.

**Formally:**

For any D0 category C:
```
C = URO + CategoryExtension(C)
```
Where CategoryExtension(C) adds fields but cannot subtract or override URO fields.

### 5.2 Depth of Specialization

D2 defines two levels of specialization depth:

**Level 1 — Category Specialization (D0 → D1):**
The 35 D0 categories specialize the URO by adding category-specific fields, setting specific LifecycleState vocabularies, and declaring specific coherence obligations.

**Level 2 — Instance Specialization (D1 → D3+):**
D3 and below may define further specializations of D1 categories for specific operational contexts. These must remain conformant to both the URO and the D1 category they specialize.

No object may skip a specialization level. A D3-level object is simultaneously a valid D1-category instance, a valid URO instance, and a valid D3-specialization.

### 5.3 Specialization Rules

**SR-1:** A specialized category must preserve every field defined in its parent specialization.

**SR-2:** A specialized category may add fields. Added fields must themselves be constitutional (legible in terms of the D1 type system).

**SR-3:** A specialized category may constrain (narrow) the cardinality or range of an inherited field. It may not widen cardinality or range.

**SR-4:** A specialized category may not add a LifecycleState that is absent from the URO universal lifecycle. It may restrict the set of valid states for its instances.

**SR-5:** No specialization may introduce deletion.

### 5.4 The Four D1.1 Categories in the Inheritance Model

**ActorProfile** specializes Entity:
```
ActorProfile = Entity + {
    ActorDimension : {
        AuthorityClaims           : [AuthorityClaim-ref]
        CompetenceDemonstrations  : [CompetenceDemonstration-ref]
        AccountabilityRecords     : [AccountabilityRecord-ref]
    }
}
```
ActorProfile is a derived representation. Its SC points to the underlying Entity's SC (same individual). There is exactly one ActorProfile per Entity; the ActorProfile does not have an independent SC.

**PossibilitySet** specializes URO (not Entity — it is a deliberative container):
```
PossibilitySet = URO + {
    DecisionRef       : CivilizationalDecision-ref  [1..1, immutable]
    PossibleActions   : [PossibleAction-ref]         [1..*, append-only during open state]
    OpenedAt          : TemporalPosition             [1..1, immutable]
    ClosedAt          : TemporalPosition | null
    State             : { open | closed }
}
```

**PossibleAction** specializes URO (distinct from CivilizationalAction):
```
PossibleAction = URO + {
    ContainerSet           : PossibilitySet-ref        [1..1, immutable]
    ActionDescription      : PropositionalContent      [1..1]
    GroundingModel         : UnderstandingModel-ref    [1..1]
    ConsiderationRationale : PropositionalContent      [1..1]
    State                  : { under-consideration | selected | rejected }
}
```

**AbstractConcept** specializes Entity:
```
AbstractConcept = Entity + {
    ReferentStatus    : { pure-abstraction | partially-grounded | reality-adjacent }
    GroundingBasis    : [EvidenceRecord-ref]    [0..*]
    DefinitionSource  : PropositionalContent    [1..1]
}
```
When ReferentStatus = pure-abstraction, GroundingBasis must be empty. When ReferentStatus ≠ pure-abstraction, GroundingBasis must be non-empty.

## PART 7: FAILURE ANALYSIS

D2 must survive stress tests. The following scenarios represent the most likely failure modes.

### F-1: The Rootless Object Problem

**Scenario:** An object is created without a traceable ExistenceAuthorization chain — e.g., during system bootstrap before FoundingRatification exists.

**Analysis:** This scenario is real. During the founding moment, FoundingRatification itself must be the first object created, and it cannot authorize its own existence through a prior chain.

**Resolution:** FoundingRatification is the unique self-authorizing object. Its ExistenceAuthorization.TerminatesAt points to itself. This is constitutionally exceptional and designated in D-2's unique root commitment. All other objects must have chains that terminate at FoundingRatification, not at themselves. Any object claiming self-authorization that is not FoundingRatification is constitutionally invalid.

### F-2: The Circular Provenance Problem

**Scenario:** Object A's ProvenanceChain references Object B, and Object B's ProvenanceChain references Object A.

**Analysis:** This constitutes a coherence violation in the Provenance Register. Circular provenance means neither object can establish a legitimate origination.

**Resolution:** Circular provenance chains are constitutionally invalid. When detected, both objects enter CoherenceViolation state in the Provenance Register. Resolution requires tracing the actual origination sequence and creating a HistoricalRecord that establishes the correct non-circular chain. One object must have originated first; the record must reflect that.

### F-3: The Orphaned Relationship Problem

**Scenario:** Object A is superseded. Object B has a URO-Relationship pointing to A (SourceObject = B, TargetObject = A). Object A is now superseded, but the relationship still points to the now-superseded A.

**Analysis:** The relationship is not invalid — it was valid when created. But it should now be updated.

**Resolution:** URO-Relationships to superseded objects are not automatically invalid. They are historically accurate. However, if the intent of the relationship was to track the current valid form of the referent, the relationship must be superseded and replaced with a new relationship pointing to A's successor. The old relationship becomes a HistoricalRecord documenting that the relationship once existed. B's CoherenceStatus must be re-evaluated in light of the supersession.

### F-4: The Identity Drift Problem

**Scenario:** An object's SemanticProfile is updated incrementally over time. After many updates, the current SM bears no resemblance to the original SM. Is this still the same object?

**Analysis:** Identity is carried by SC, not SM. If SC is unchanged, it is the same object regardless of SM drift. SM drift is constitutionally permitted — it represents the object's semantic evolution.

**Resolution:** SM drift is valid so long as: (a) each SM change generates a ChangeRecord, (b) the SC is never modified, and (c) the chain of ChangeRecords is complete and unbroken. If a reviewer finds the drift so radical that the object's CategoryMembership appears to have changed, that is a Ontological Register coherence violation — the CategoryMembership is part of SC and cannot change. If it must change, the result is a Supersession, not an update.

### F-5: The Epistemic Chain Skip Problem

**Scenario:** An agent asserts a KnowledgeClaim without having traceable EvidenceRecords — e.g., by asserting that something is known on the basis of authority alone.

**Analysis:** Authority is not evidence. A KnowledgeClaim must have JustificationPath tracing through EvidenceRecord. Authority determines who may assert a KnowledgeClaim; it does not substitute for the evidential grounding the claim requires.

**Resolution:** The object is constitutionally incomplete. It may not enter Active state. If it is already Active (a legacy or import case), it enters a CoherenceViolation state in both the Epistemic Register and the Provenance Register. Resolution requires either: (a) providing the missing evidential chain retroactively, or (b) reclassifying the object to a lower ChainPosition (e.g., from KnowledgeClaim to Belief, which does not require validation) and superseding the original.

### F-6: The TerminalValue Generation Problem

**Scenario:** An agent reasons its way to a new TerminalValue that was not established by FoundingRatification.

**Analysis:** A-V1 prohibits internal generation of TerminalValues. An agent may identify that an existing TerminalValue has implications not previously recognized — but it may not originate a new TerminalValue.

**Resolution:** If an agent produces what appears to be a new TerminalValue, it must be classified as an InstrumentalValue (derivative of existing TerminalValues) or as an AbstractConcept that the agent is confusing with a TerminalValue. Its ExistenceAuthorization chain will reveal the problem: it cannot terminate at FoundingRatification for TerminalValue purposes because FoundingRatification did not ratify this value. The object must be reclassified. If the civilization genuinely requires a new TerminalValue, that requires a refounding event — constitutionally the most heavyweight possible process.

### F-7: The ActorProfile Authority Confusion Problem

**Scenario:** An ActorProfile is treated as an authority source — e.g., "ActorProfile X authorized this."

**Analysis:** ActorProfile is a derived representation of an Entity's actor-capacity history. It aggregates AuthorityClaims but does not itself hold or grant authority.

**Resolution:** Authorization always flows from AuthorityClaim → AuthoritySource → FoundingRatification. The ActorProfile is a convenience view; the authoritative record is the AuthorityClaim itself. Any authorization attributed to an ActorProfile must be re-read as attribution to the underlying AuthorityClaim that the ActorProfile aggregates.
