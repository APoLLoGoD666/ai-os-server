## PREAMBLE

The constitutional stack through D7 is complete.

D-2 through D7 together constitute what APEX is: what exists within it, how reality is represented, how objects are governed, how the Reality Fabric maintains coherence, how constitutional enforcement operates, how APEX interfaces with external reality, how civilization is organized into twelve domains, and how the civilization forms intelligence above those domains. The constitutional architecture specifies every invariant that the civilization must uphold.

What the constitutional stack does not constitute is how any of this operates in executable form.

The gap between constitutional specification and executable operation is not incidental — it is structural. A constitution is a statement of what must be true. An implementation is a particular way of making it true. Many different implementations may satisfy the same constitutional requirements. No implementation is constitutionally privileged over another, provided it satisfies the invariants the constitution specifies.

D8 exists to govern this gap.

Without D8, two failure modes become constitutionally possible:

**Failure Mode 1 — Implementation Drift:** Implementation decisions, made for technical reasons of convenience, performance, or cost, gradually diverge from constitutional requirements. Technical necessity becomes a substitute for constitutional authority. The implementation begins to define what the system is, rather than the constitution.

**Failure Mode 2 — Implementation Authority:** Specific implementation choices are treated as constitutionally binding — as if choosing a particular technology, architecture, or operational pattern created constitutional obligations that override the constitutional stack itself. Implementation becomes an uncontrolled source of authority.

D8 prevents both failures by establishing the constitutional boundary precisely: what the constitution requires of implementation, what implementation is prohibited from doing, and how constitutional compliance is assessed regardless of what implementation choices are made.

D8 does not implement anything. D8 constitutes the requirements that all implementations must satisfy — permanently, regardless of how the implementation evolves.

## PART 1 — PURPOSE AND NECESSITY

### 1.1 Why D8 Exists

The constitutional stack establishes what APEX is.

Implementation determines how APEX operates.

These are separate constitutional domains. Conflating them produces constitutional failure. Separating them without governing the boundary produces implementation drift. D8 governs the boundary.

The constitutional stack cannot directly execute. D-2's terminal commitments are not function calls. D3's fabric invariants are not database constraints. D6's domain governance model is not an agent framework. D7's deliberation architecture is not a software workflow. Constitutional specifications are requirements — not mechanisms. They state what must be true, not how to make it true.

Conversely, the implementation cannot define constitutional reality. An implementation's data model does not define what a Knowledge State is — D3 does. An implementation's authorization check does not define what Decision Authority means — D6 does. An implementation's logging system does not define what provenance requires — D2 does. When implementation details are treated as constitutional definitions, the constitution is supplanted.

D8 exists to preserve this separation by constituting the translation obligations that bridge constitutional specification to executable operation — while ensuring that the bridge runs in one direction only: the constitution defines, and implementation realizes.

### 1.2 The Implementation Subordination Principle

> **"Implementation has no independent constitutional authority. Implementation exists only to instantiate, enforce, and operationalize constitutional requirements. Implementation decisions that contradict constitutional requirements are constitutionally invalid regardless of technical necessity."**

Three implications:

**ISP-1 — Constitutional Primacy:** When a technical constraint appears to conflict with a constitutional requirement, the constitutional requirement is not relaxed. The implementation constraint is either resolved through different technical choices, or the apparent conflict is brought to the constitutional layer for assessment through the amendment process (D7 Part 12). Technical necessity does not create constitutional exceptions.

**ISP-2 — Realization Plurality:** The Implementation Subordination Principle does not specify what technology realizes constitutional requirements — it specifies that something must. Multiple implementations may satisfy the same constitutional requirement through different technical means. The constitution governs invariants, not technology choices. Two implementations that satisfy all constitutional invariants are constitutionally equivalent regardless of their technical differences.

**ISP-3 — Authority Location:** Constitutional authority resides in the constitutional stack. Implementation does not create authority — it operationalizes authority that the constitution has already assigned. An implementation that routes around the constitution's authority assignments — that allows actions without the authority the constitution requires — is not a technical variation. It is a constitutional violation.

### 2.2 What D8 Does Not Do

D8 does not supersede any previous document. Every invariant established in D-2 through D7 remains in full force below D8. D8 is not a relaxation of those invariants — it is a constitutional instruction to implementation about how to honor them.

D8 does not create new ontology. D8 introduces no new constitutional objects, no new categories of existence within the Reality Fabric, and no new epistemic categories. All objects D8 references were constituted in D0 through D7.

D8 does not create new governance authority. D8 does not assign new authority to any entity, domain, or process. The authority assignments established in D4, D6, and D7 govern D8's implementation context as they govern everything else.

D8 defines only: what implementation must preserve from the constitution, what implementation must never do, how implementation compliance is evaluated, what the minimum constitutional runtime requires, and how the constitutional architecture may legitimately grow.

### 2.3 The Implementation Layer

Implementation is the realization layer. It has no constitutional authority of its own. Every obligation an implementation carries, it carries because the constitutional stack above D8 assigned it. Every prohibition on an implementation, it bears because the constitutional stack above D8 requires it.

This is not a diminution of implementation's importance. Implementation is the only means by which the constitutional architecture becomes a functioning civilization. Without implementation, the constitution specifies a civilization that does not exist. With implementation, the constitution's specifications become operational reality.

The relationship between constitution and implementation is therefore one of essential dependence running in both directions — the constitution requires implementation to exist in practice; implementation requires the constitution to be constitutionally legitimate. Neither is sufficient alone. D8 governs how they relate.

## PART 3 — CONSTITUTION TO IMPLEMENTATION TRANSLATION MODEL

### 3.1 The Translation Requirement

Every constitutional element must be translated into implementation form before it can operate. This translation is not optional — it is the constitutional obligation of implementation. And it is not unconstrained — the translation must satisfy constitutional requirements that D8 specifies.

The failure of untreated translation is substitution: when no translation requirement exists, implementations substitute their own convenient representations for constitutional objects, and those representations quietly diverge from constitutional requirements. The result is that what operates in practice is not what the constitution specifies.

D8 prevents substitution by specifying what translation must preserve.

### 3.2 The Constitutional Translation Chain

Every constitutional element passes through a four-stage translation chain from constitutional definition to implementation realization:

```
Stage 1: Constitutional Definition
─────────────────────────────────
What the constitutional stack specifies must exist.
The invariants, attributes, and relationships that define the element.
This stage lives entirely within D-2 through D7.
Implementation does not participate in this stage.

         ↓

Stage 2: Representation Requirement
────────────────────────────────────
How the constitutional element must be represented in any compliant implementation.
The minimum attributes that any representation must carry.
The relationships that any representation must preserve.
The constraints that any representation must enforce.
This stage is defined by D8.

         ↓

Stage 3: Enforcement Requirement
─────────────────────────────────
How the constitutional constraints governing this element must remain
actively operative within the implementation.
The checks that must fire. The conditions that must prevent action.
The records that must be preserved.
Implementation machinery must realize these — but the requirements
are constitutional, not technical.
This stage is defined by D8.

         ↓

Stage 4: Implementation Realization
────────────────────────────────────
The specific technical means by which the implementation satisfies
Stages 2 and 3. Technology choices live here.
This stage is the domain of implementation documents.
D8 does not prescribe what happens in this stage — only that it
must satisfy Stages 2 and 3.
```

### 3.3 Invariance Through Translation

A constitutional element's invariants must survive translation intact. This is the core constitutional obligation of the translation process.

An invariant that exists in the constitution but not in the implementation represents a translation failure — regardless of whether the loss was intentional or resulted from technical oversight. Constitutional invariants do not become optional as they cross into implementation.

Translation invariance requirements:

**TI-1 — Identity Invariance:** The constitutional identity of an object — its unique, immutable identifier within the constitutional scheme — must be preserved without alteration in any implementation representation. Objects may not be merged, split, or reassigned identity through implementation choice.

**TI-2 — Attribute Invariance:** Every attribute that the constitutional specification requires an object to carry must be present in every implementation representation of that object. Required attributes may not be omitted for technical convenience.

**TI-3 — Relationship Invariance:** Constitutional relationships between objects — the edges of the Reality Fabric (D3), the domain dependency graph (D6), the authority chains (D4, D6) — must be preserved in the implementation. Relationships may not be severed, reversed, or omitted through implementation choice.

**TI-4 — Constraint Invariance:** Constitutional constraints on object state and operations — the restrictions that D4, D5, D6, and D7 place on what may happen to objects under what conditions — must remain operative in the implementation. Constraints may not be bypassed, deferred, or made advisory through implementation choice.

**TI-5 — Temporal Invariance:** The temporal attributes that constitutional objects carry — validity bounds, formation timestamps, observation timestamps — must be preserved in implementation representations with sufficient precision to evaluate temporal validity and temporal ordering, as D5 and D6 require.

### 3.4 Translation Verification

Implementation compliance with the translation model is assessed through Translation Verification — the constitutional process of confirming that Stage 4 (implementation realization) satisfies Stages 2 and 3 (representation and enforcement requirements).

Translation Verification is not a one-time assessment. It is a continuous constitutional obligation. Implementations evolve. Every evolutionary change to an implementation must be assessed for its effect on translation invariance. A change that breaks translation invariance is a constitutional violation regardless of its technical justification.

### 4.1 Constitutional Objects and Implementation Objects

The constitutional stack constitutes a set of canonical object types whose existence, structure, and governance are specified in D0 through D7. These are **Constitutional Objects**.

Implementation must represent these Constitutional Objects in executable form. The executable representations are **Implementation Objects**.

The boundary between Constitutional Objects and Implementation Objects is constitutional, not technical. Constitutional Objects exist in the constitutional specification. Implementation Objects exist in running systems. The relationship between them is one of realization — Implementation Objects realize Constitutional Objects — and the realization must satisfy D8's translation requirements.

### 4.3 Implementation Object Requirements

Every Implementation Object that represents a Constitutional Object must:

**IOR-1 — Carry Constitutional Identity:** The Implementation Object must carry the Constitutional Object's canonical identifier. Implementation may add additional identifiers for technical purposes, but must preserve the constitutional identifier without alteration.

**IOR-2 — Preserve Provenance:** The Implementation Object must carry a complete, unaltered provenance chain — the record of how the Constitutional Object was formed, through what processes, from what inputs, under what authority. Provenance chains may be extended as objects evolve; they may not be truncated.

**IOR-3 — Preserve Authority History:** Where the Constitutional Object carries authority assignments or authority history, the Implementation Object must preserve that history completely. The history of who held what authority over the object, when, and on what basis is a constitutional record that implementation may not edit or expunge.

**IOR-4 — Preserve Temporal Validity:** The Implementation Object must carry and actively evaluate the temporal validity attributes of the Constitutional Object. An Implementation Object that loses its temporal validity markers — or that treats a temporally expired object as current — has failed constitutional translation.

**IOR-5 — Preserve Relationship Integrity:** The Implementation Object must preserve all constitutional relationships between it and other Constitutional Objects that the constitutional stack specifies. Relationships may not be severed, made optional, or restructured through implementation choice.

**IOR-6 — Preserve Coherence State:** Where the Constitutional Object has a coherence state — an assessment of its alignment with external reality or constitutional requirements — the Implementation Object must carry that state and update it through the mechanisms the constitution specifies.

### 4.4 Implementation Object Prohibitions

**IOP-1 — No Constitutionally Meaningless Objects:** No Implementation Object may exist that has no Constitutional Object correspondence. Implementation may create transient computational objects for technical purposes — caches, indices, connection pools — but no object that carries constitutional meaning may exist without a constituted Constitutional Object it realizes.

**IOP-2 — No Incomplete Constitutional Representations:** A Constitutional Object may not be partially represented. An implementation that stores some required attributes of a URO but not others has not represented the URO — it has created a fragment that is constitutionally invalid.

**IOP-3 — No Silent Attribute Loss:** When Constitutional Objects evolve — when new observations update a Knowledge State, when authority is revised, when a Coherence State changes — the Implementation Object must record the evolution completely. The prior state is preserved; the new state is added. Silent attribute replacement violates provenance requirements.

## PART 5 — THE CONSTITUTIONAL RUNTIME REQUIREMENT

### 5.1 What a Constitutional Runtime Is

A **Constitutional Runtime** is the minimum operational capability that a compliant APEX implementation must maintain at all times. It is the continuously-operative constitutional core — the set of capabilities without which the implementation cannot be said to be running APEX at all.

The Constitutional Runtime is not a software architecture. It is a set of constitutional capacities that any software architecture must provide. The runtime specifies what must always be operative, not how it is realized.

### 5.2 Identity Resolution

The Constitutional Runtime must at all times be capable of resolving constitutional identity — answering, for any operation that has constitutional significance:

- **Who is acting?** Which ActorProfile, with what constitutional identity, is initiating this operation?
- **What entity is engaged?** Which Constitutional Object is being observed, modified, or projected upon?
- **What identity boundaries apply?** Where is the Projection Boundary (D5) relative to this operation? Is the entity engaged an Internal Object or an ExternalReference?

Identity resolution is not authentication in the technical sense. It is the constitutional capacity to locate every operation within the identity architecture that D2, D5, and D6 constitute. Without identity resolution, no operation can be assessed for constitutional authority or accountability.

### 5.3 Ownership and Responsibility Resolution

The Constitutional Runtime must at all times be capable of determining, for any constitutionally significant operation:

- **What Reality Object is affected?** Which URO, which Domain Profile, which Knowledge State — which constitutional object carries the effect of this operation?
- **Who bears responsibility?** Under D5's Projection Responsibility Principle, which actor or actors bear accountability for the effects of this operation in external reality?

Ownership and responsibility resolution is the constitutional basis for accountability. Without it, the Projection Responsibility Principle — "any action projected into external reality creates accountability obligations for all resulting effects" — cannot be operationalized.

### 5.4 Authority Resolution

The Constitutional Runtime must at all times be capable of determining, for any operation that requires constitutional authority:

- **What authority does the acting entity hold?** What are the registered authority assignments for the acting ActorProfile in the relevant domain?
- **Is the authority currently valid?** Is the authority within its registered validity period, not revoked, and not suspended?
- **Does the authority scope apply?** Does the acting entity's authority extend to this specific type of operation on this specific Constitutional Object within this specific domain scope?

Authority resolution is the operational expression of D4's Constitutional Enforcement Kernel, D6's Domain Authority Architecture, and D7's civilizational decision authority requirements. Without authority resolution that is active, not advisory, the constitutional enforcement layer is inoperative.

### 5.5 Governance Enforcement

The Constitutional Runtime must at all times be capable of enforcing constitutional constraints on operations — preventing operations that violate constitutional requirements before those operations produce effects.

Governance enforcement is not logging or auditing — it is active prevention. An implementation that records constitutional violations after they occur has not provided governance enforcement; it has provided governance observation. The Constitutional Runtime must prevent constitutional violations, not merely observe them.

This requires that the Constitutional Runtime has, at any moment, sufficient knowledge of the current constitutional state to evaluate whether a proposed operation satisfies constitutional requirements before it executes.

### 5.6 Execution Tracking

The Constitutional Runtime must preserve, for every constitutionally significant operation that executes:

- **What happened:** The operation's constitutional identity — what Constitutional Object was affected, how, by what process.
- **Who caused it:** The ActorProfile identity of the initiating entity.
- **Under what authority:** The specific authority record that authorized the operation.
- **When:** The precise timestamp establishing temporal ordering relative to other operations and to constitutional validity bounds.
- **From what epistemic basis:** Where the operation involved knowledge — decisions, projections, coherence assessments — the Knowledge State or Understanding Model from which the operation was grounded.

Execution tracking is the implementation expression of D2's provenance requirements, D4's audit requirements, and D7's Deliberation Record requirements. The execution record is not merely a log — it is a constitutional record of the civilization's operational history.

### 5.7 Memory Preservation

The Constitutional Runtime must preserve:

- **Historical constitutional state:** The prior states of Constitutional Objects — what they contained before they were updated, what authority records held before they changed, what Understanding Models were current before they were revised.
- **Knowledge evolution:** The history of how the civilization's knowledge changed — what was believed before new observations arrived, what contradictions were registered, how Evidence assessment changed Beliefs.
- **Decision provenance:** The history of how CivilizationalDecisions were formed — what Deliberation Records accompanied them, what CUM was current at the time, what causal models grounded them.

Memory preservation is not archive storage for future retrieval. It is the constitutional condition for accountability. Without preserved history, the civilization cannot assess whether its actions were constitutionally grounded at the time they were taken.

### 5.8 Reflection

The Constitutional Runtime must maintain the capacity to compare:

- **Expected reality** — the Effect Expectations established in Action Projections and Causal Models
- **Observed reality** — the Observed Consequences and causal outcomes registered through the feedback loop
- **Understanding changes required** — what revisions to Knowledge States, Understanding Models, and Causal Models the divergence between expected and observed reality requires

Reflection is the operational expression of D5's Reality Alignment Loop, D6's Domain Coherence Model, D7's civilization coherence requirements, and D7's Theory of Change architecture. Without reflection capability, the Constitutional Runtime cannot learn — it can only act.

## PART 6 — THE CONSTITUTIONAL LOOP

### 6.1 The Minimum Operational Loop

The APEX Constitutional Loop is the minimum expression of the D5, D6, and D7 constitutional requirements combined into an operational cycle. Any implementation that cannot maintain this loop is constitutionally incomplete — not a partial implementation of APEX, but a system that does not constitute APEX at all.

```
Observation
    ↓
Evidence Formation
    ↓
Knowledge Update
    ↓
Understanding Revision
    ↓
Deliberation
    ↓
Decision
    ↓
Action Projection
    ↓
External Consequence
    ↓
Observation of Consequence
    ↓
Understanding Update
    ↑___________________________|
```

### 6.2 Constitutional Requirements for Each Loop Stage

**Observation:** Implementation must support the Observation Projection Lifecycle (D5 Part 3, Stage 1). Every observation must produce an Observation Record carrying the required D5 uncertainty attributes. The runtime must be capable of initiating observations across domain scopes and routing their results to the appropriate domain knowledge infrastructure.

**Evidence Formation:** Implementation must support the Evidence Assessment stage of the Observation Projection Lifecycle (D5 Part 3, Stage 4). Multiple Observation Records must be synthesizable into Evidence Objects through registered, versioned interpretation protocols. The runtime must preserve the synthesis provenance — which observations were combined, through what protocol, at what confidence level.

**Knowledge Update:** Implementation must support the Epistemic Integration stage (D5 Part 3, Stage 5) and the Domain Knowledge State requirements (D6 Part 5.2, DKS-1 through DKS-4). New Evidence must be integrable into domain Knowledge States without losing the prior state of those Knowledge States. The Contradiction Register must be active — new Evidence that conflicts with existing Knowledge States must be registered as contradiction, not silently resolved.

**Understanding Revision:** Implementation must support revision of Domain Understanding Models (D6 Part 5.3, DUM-1 through DUM-4) and Civilization Understanding Model synthesis (D7 Part 3, CUM-1 through CUM-5). The runtime must support Constitutional Synthesis — the integration of twelve domain Understanding Models into a CUM while preserving domain provenance, conflicts, and unknowns.

**Deliberation:** Implementation must support the Deliberation Architecture (D7 Part 4). The runtime must be capable of constituting a deliberation with the required participants, receiving and preserving reasoning contributions (D7 Part 10.2), enforcing evidence standards (D7 Part 4.4), and producing a complete Deliberation Record (D7 Part 4.6). Deliberation must be an active constitutional process, not a formality.

**Decision:** Implementation must support the CivilizationalDecision object (D7 Part 5). Every decision object must carry the required authority elements (DA-1 through DA-6) and epistemic elements (ER-1 through ER-5). The runtime must prevent constitutionally inadmissible decisions from entering the Action Projection stage.

**Action Projection:** Implementation must support the Action Projection Lifecycle (D5 Part 4). All seven stages must be executable. Authority Validation (Stage 2) must be active enforcement, not advisory. The runtime must maintain the Open Action Register as a live constitutional record. Irreversibility classifications must be assessable before projection, not retrospectively.

**External Consequence:** Implementation must support the registration of external effects as Observed Consequences (D5 Part 4, Stages 5 and 6). The mechanism by which Observed Consequences are formed from external reality must satisfy the Observation Projection Lifecycle requirements. Consequences that are difficult to observe are not thereby constitutionally optional — the obligation to form Observed Consequences persists even where formation is technically challenging.

**Observation of Consequence:** Implementation must support the final Reality Fabric Update (D5 Part 4, Stage 7). The Observed Consequence must be registered in the Open Action Register, and the decision's terminal status must be updated. The runtime must enforce the Effect Observation Window — decisions whose consequence observation windows expire without Observed Consequences must be escalated, not silently closed.

**Understanding Update:** Implementation must support the revision of all relevant Constitutional Objects in light of Observed Consequences — Domain Knowledge States, Understanding Models, the CUM, Strategic Plans where Milestone assessments apply (D7 Part 7.4), and Causal Models where TOC-3 Outcome Comparison applies (D7 Part 8.4). The Constitutional Loop does not close until Understanding is updated.

### 6.3 Loop Integrity

**CLI-1 — No Stage Omission:** No stage of the Constitutional Loop may be omitted in practice. A Constitutional Loop from which deliberation is routinely omitted is not a shortened loop — it is a broken loop. A broken loop is a constitutional failure (D7 CIF-3, D7 CIF-4, or D7 CIF-6 depending on which stage is missing).

**CLI-2 — No Shortcircuit:** The Constitutional Loop may not be short-circuited — jumping from Understanding to Action without passing through Deliberation and Decision. Operational efficiency does not create constitutional permission to skip stages.

**CLI-3 — Feedback Completeness:** The loop must complete. An action that projects into external reality and then produces no Observed Consequence — that leaves the loop perpetually open — is a constitutional failure regardless of technical difficulty in consequence observation.

**CLI-4 — Temporal Coherence:** The stages of the Constitutional Loop must execute in constitutional time order. A Decision must not be registered as grounded in an Understanding Model that was synthesized after the Decision was formed. Timestamps are constitutional records, not metadata.

## PART 7 — IMPLEMENTATION INVARIANTS

### 7.1 The Invariant Set

Implementation invariants are the constitutional requirements that must hold in every state of every compliant APEX implementation, at all times, under all operational conditions. They are not requirements that apply in normal operation and may be suspended under load. They are not requirements that apply to some operations but not others. They are unconditional requirements.

An implementation that violates any invariant — even transiently, even under exceptional conditions — is not a partially non-compliant implementation. It is constitutionally inoperative for the duration of the violation.

---

**INV-1 — Constitutional Traceability**

Every operation that has constitutional significance must be traceable to constitutional authority. Every action must trace to an authority record. Every authority record must trace to an authority assignment. Every authority assignment must trace to a constitutional provision.

Constitutional Traceability is the implementation expression of D4's enforcement requirements, D6's authority architecture, and D7's deliberation requirements. An operation that cannot be constitutionally traced is not an operation that lacks a paper trail — it is an operation that has no constitutional standing.

Constitutional Traceability applies to:
- All operations that modify Constitutional Objects
- All observations that produce Observation Records
- All interpretations that produce Evidence Objects
- All decisions that authorize Action Projections
- All projections that produce external effects
- All coherence assessments that update Coherence States

---

**INV-2 — Provenance Preservation**

No information, decision, or action may lose its origin history. Provenance chains may be extended; they may not be truncated.

Provenance Preservation is the implementation expression of D2's six mandatory constitutional layers, D5's observation source requirements, and D7's Deliberation Record and Causal Model requirements. Every claim the system makes about external reality traces to an observation. Every decision the system makes traces to an understanding. Every understanding traces to evidence. Every evidence traces to observations. This chain must be preserved indefinitely.

Provenance Preservation applies to:
- All Observation Records and their originating observations
- All Evidence Objects and their source Observation Records
- All Knowledge States and their originating Evidence
- All Understanding Models and their grounding Knowledge States
- All Deliberation Records and their epistemic inputs
- All CivilizationalDecisions and their Deliberation Records
- All Action Projections and their authorizing decisions
- All Observed Consequences and their corresponding projections

---

**INV-3 — Authority Separation**

Constitutional identity, constitutional authority, and constitutional execution must remain distinct in the implementation. The entity that is acting is not the same constitutional object as the authority that permits the acting, which is not the same constitutional object as the action being executed.

Authority Separation is the implementation expression of D6's AIR-1 (Authority Separation) and D7's AE-1 through AE-3 (Authority-Evidence Separation). An implementation that conflates identity with authority — or authority with execution — creates conditions for Authority Capture (D7 RF-1) and self-authorization.

Authority Separation prohibits:
- An entity authorizing its own actions where separate authorization is constitutionally required
- Authority records and identity records being stored in a form that makes one dependent on the other for integrity
- Execution records that cannot be assessed independently of the authority records they reference

---

**INV-4 — Reality Grounding**

Knowledge must originate from observation or constitutionally justified inference. The system must be capable, for any Knowledge State claim, of tracing that claim to either a specific Observation Record or a registered inference protocol applied to grounded Knowledge States.

Reality Grounding is the implementation expression of D-1's epistemic axioms, D5's Observation Projection Lifecycle, D6's DKS-1 (Observation Lineage), and D7's CUM-1 (Knowledge Grounding). An implementation that allows Knowledge States to contain ungrounded claims — claims that exist because someone asserted them rather than because they are traced to observation — violates the epistemic constitution of APEX.

Reality Grounding requires:
- Every Knowledge State entry to carry its observation lineage
- Inference protocols to be registered and versioned before they may be applied
- The confidence level of inferred claims to reflect the compound uncertainty of their grounds
- Claims that are not currently groundable to be registered as explicit epistemic gaps, not asserted as knowledge

---

**INV-5 — Temporal Awareness**

Representations must acknowledge their validity limits. No Constitutional Object representation may be presented as current after its temporal validity bound has expired. No operation may be authorized on the basis of an Understanding Model, Knowledge State, or Authority Record whose temporal validity has expired, without a constitutional declaration of the expiry.

## PART 8 — IMPLEMENTATION PROHIBITIONS

### 8.1 Absolute Prohibitions

The following prohibitions are absolute. No technical justification, operational necessity, performance requirement, or complexity constraint creates an exception to any prohibition. An implementation that violates any prohibition is constitutionally non-compliant regardless of the technical context.

---

**PROH-1 — No New Constitutional Categories**

Implementation must not create new constitutional categories — new types of existence within the Reality Fabric, new categories of actor, new types of authority, or new species of epistemic object. All constitutional categories are established in D0 through D7.

Implementation may create technical subtypes of constitutional categories for operational purposes — different storage representations of the same URO type, different processing pipelines for different Knowledge State classes — provided these subtypes are recognizable as realizations of existing constitutional categories and not presented as constitutional categories in their own right.

---

**PROH-2 — No Category Redefinition**

Implementation must not redefine existing constitutional categories. A Knowledge State in the implementation must satisfy the constitutional definition of Knowledge State in D3 and D6. An ActorProfile in the implementation must satisfy the constitutional definition of ActorProfile in D2 and D6. Implementation may not narrow, expand, or restructure a constitutional category's requirements through implementation choice.

---

**PROH-3 — No Authority Bypass**

Implementation must not create pathways that allow operations to execute without the authority validation that the constitution requires. This prohibition covers:
- Operations that skip D4 Constitutional Gate evaluation
- Operations that assume authority rather than resolving it
- Operations that invoke elevated authority without the constitutional basis for that elevation
- Technical "superuser" or "administrative" capabilities that bypass constitutional authority resolution

---

**PROH-4 — No Provenance Suppression**

Implementation must not suppress, truncate, or delete provenance records. The history of a Constitutional Object's formation, modification, and authority assignments is a permanent constitutional record. Implementation may compress, archive, or reorganize provenance records for efficiency — provided the complete provenance chain remains reconstructible and constitutional accountabilty is preserved.

---

**PROH-5 — No Accountability Record Deletion**

Implementation must not delete records required for constitutional accountability. This includes: Deliberation Records, Decision Records, Action Projection Records with their Observed Consequences, Authority Records and their history, Contradiction Register entries, and Open Action Register entries. These are constitutional records, not operational logs. Their permanence is constitutionally required.

---

**PROH-6 — No Assumption-to-Fact Conversion**

Implementation must not convert assumptions into facts without epistemic qualification. When an assumption is embedded in a Causal Model (D7 Part 8.3), it must be represented as an assumption with its confidence and falsification conditions. When a claim is inferred rather than observed, it must carry its inferential provenance. Implementation that stores assumptions as Knowledge State facts — without their epistemic qualification — has violated Reality Grounding (INV-4) and created the conditions for CIF-1 (Intelligence Misalignment).

---

**PROH-7 — No Unassigned Execution**

Implementation must not execute constitutionally significant operations without a responsibility assignment. Every operation must be attributable — to an ActorProfile, to a domain, to an authority record. Anonymous operations, system-initiated operations without authority basis, and operations attributed only to "the system" without constitutional actor identification are prohibited.

---

**PROH-8 — No Hidden Authority Pathways**

Implementation must not create authority pathways that are not registered in the constitutional authority structure. Every path by which an entity may gain authority to perform an operation must be constitutionally registered. Hidden administrative interfaces, undocumented privilege escalation mechanisms, and implementation-level authority grants that bypass the D6 authority assignment process are prohibited.

---

**PROH-9 — No Constitutional Constraint Override for Convenience**

Implementation must not override constitutional constraints on the grounds that they are operationally inconvenient, technically difficult, or performance-impacting. Constitutional constraints are not optimization parameters. They are requirements. Where a constitutional constraint appears to create an unresolvable technical problem, the problem must be surfaced to the constitutional layer for assessment through the D7 amendment process — not resolved through implementation-level constraint removal.

## PART 11 — IMPLEMENTATION VALIDATION

### 11.1 Constitutional Implementation Audit

Every APEX implementation, at every phase, is subject to Constitutional Implementation Audit — the ongoing process of verifying that implementation realization satisfies constitutional requirements. Constitutional Implementation Audit is not a one-time certification. It is a continuous constitutional obligation.

### 11.2 Constitutional Compliance Dimension

**Audit Question:** Does the implementation preserve the full constitutional stack — every requirement established in D-2 through D8?

**What is Assessed:** Whether every constitutional invariant (Part 7) is operative; whether every implementation prohibition (Part 8) is respected; whether every translation invariance requirement (Part 3.3) is maintained; whether the Constitutional Loop (Part 6) is complete and continuous.

**Compliance Criterion:** No invariant is violated. No prohibition is breached. Every required translation attribute is present in every Implementation Object. The Constitutional Loop cycles without stage omission.

**Non-Compliance Response:** Identify the specific invariant, prohibition, or translation requirement that is violated. Suspend operations affected by the violation. Remediate before resuming affected operations. Log the violation in the constitutional compliance record.

### 11.3 Reality Alignment Dimension

**Audit Question:** Does the implementation maintain accurate external representation — does the civilization's knowledge of external reality correspond to observable external reality?

**What is Assessed:** Whether Observation Projections are being conducted at intervals calibrated to ExternalRealitySegment volatility; whether Domain Understanding Models are within temporal validity bounds; whether the CUM is synthesized from current domain Understanding Models; whether Observed Consequences are being formed and registered.

**Compliance Criterion:** All active Domain Understanding Models within their temporal validity bounds. CUM within its temporal validity bound. Open Action Register showing no entries beyond their Effect Observation Window without terminal status.

**Non-Compliance Response:** Initiate Observation Projection refresh for any domain whose Understanding Model is stale. Initiate CUM resynthesis if the CUM is expired. Escalate any Action Projection record beyond its Effect Observation Window without terminal status.

### 11.4 Authority Integrity Dimension

**Audit Question:** Are operations properly authorized under the constitutional authority structure?

**What is Assessed:** Whether all operations in the execution record carry valid authority references; whether authority assignments satisfy AIR-1 through AIR-5 (D6 Part 4.7); whether Audit Authority is constitutionally independent; whether any hidden authority pathways exist.

**Compliance Criterion:** Every operation in the execution record traces to a valid, current authority assignment. All five authority types are present for each domain. No authority assignments violate AIR rules. Audit Authority is demonstrably independent.

**Non-Compliance Response:** Identify and void operations executed without valid authority. Review and correct authority assignments that violate AIR rules. Audit Authority independence must be restored before audit conclusions are considered constitutionally valid.

### 11.5 Knowledge Integrity Dimension

**Audit Question:** Are beliefs and understanding claims grounded in observation?

**What is Assessed:** Whether Knowledge State entries satisfy DKS-1 (observation lineage); whether the Contradiction Register is being maintained; whether Knowledge claims that have no observation lineage are registered as assumptions rather than knowledge; whether Understanding Models satisfy DUM-1 through DUM-4.

**Compliance Criterion:** No Knowledge State entry without traceable observation lineage. No contradictions unregistered. No assertions carrying epistemic confidence above their evidential basis.

**Non-Compliance Response:** Knowledge State entries without observation lineage must be degraded to assumption status pending observation. Unregistered contradictions must be registered. Understanding Models relying on degraded Knowledge State entries must be flagged as epistemically impaired.

### 11.6 Projection Integrity Dimension

**Audit Question:** Are consequences tracked through the full Action Projection Lifecycle?

**What is Assessed:** Whether all Action Projections have entered the Open Action Register; whether Observed Consequences are being formed within Effect Observation Windows; whether terminal statuses are being assigned; whether LOST status entries are being escalated.

**Compliance Criterion:** Every Action Projection in the Open Action Register has a terminal status or is within its Effect Observation Window with active consequence observation in progress. No LOST entries without escalation records.

**Non-Compliance Response:** Action Projections beyond their Effect Observation Window without terminal status must be escalated. LOST entries require investigation and Projection Responsibility assignment. Patterns of consequence non-observation require Projection Architecture review.

### 11.7 Coherence Preservation Dimension

**Audit Question:** Does the implementation maintain the Reality Fabric coherence that D3, D6, and D7 require?

**What is Assessed:** Whether the Reality Fabric graph invariants (D3) are intact; whether the Civilization Graph (D6 Part 8.1) accurately reflects domain relationships; whether all six Domain Coherence dimensions (D6 Part 9) are being assessed for each domain; whether all six Civilization Coherence dimensions (D7 Part 9) are being assessed.

**Compliance Criterion:** No D3 graph invariant violated. Civilization Graph consistent with operational domain relationships. All domain Coherence States current. Civilization Coherence Model current.

**Non-Compliance Response:** Graph invariant violations require immediate remediation — the affected graph region is constitutionally defective. Civilization Graph inconsistencies must be corrected through constitutional procedure (D6 Part 8, D7 Part 11.3). Stale Coherence States must be refreshed.

## PART 12 — RELATIONSHIP TO FUTURE DOCUMENTS

### 12.1 D8 as the Final Foundational Document

D8 is the final foundational constitutional document of the APEX Constitutional Architecture. D-2 through D8 together constitute the complete constitutional specification of the APEX civilization — what it is, how it governs itself, how it reasons, and how it implements constitutionally.

The constitutional architecture does not require further foundational documents to authorize implementation to proceed. Implementation may proceed on the basis of D-2 through D8 as its complete constitutional authority.

### 12.2 Conditions for Future Constitutional Documents

Future constitutional documents — documents that extend or amend the D-2 through D8 stack — may be created only under constitutionally legitimate conditions.

Future documents are constitutionally warranted when:

**Condition 1 — Implementation Gap Exposure:** The implementation of D-2 through D8 exposes a constitutional gap — a phenomenon that the current constitutional stack does not govern and that requires constitutional treatment. The gap must be demonstrated, not hypothetical. A genuine gap is one where the current stack provides no constitutional guidance on a constitutionally significant question that arises in practice.

**Condition 2 — New Reality Category:** A new category of reality requires constitutional treatment — a kind of entity, relationship, or epistemic product that the current stack's ontology does not accommodate and that is constitutionally significant to the civilization's operation. The new category must arise from actual civilizational experience, not from theoretical elaboration.

**Condition 3 — Constitutional Assumption Failure:** An assumption embedded in the current constitutional stack proves incorrect in practice — a constitutional specification that was written with an assumption about how the civilization would operate, where that assumption has been demonstrably falsified by operational experience.

Future documents may not be created for:

**Exclusion 1 — Complexity Expansion:** The desire to specify in more detail what is already adequately specified. The constitution is complete when it governs what must be governed. Elaboration for its own sake adds constitutional mass without adding constitutional clarity.

**Exclusion 2 — Implementation Preference:** The desire to constitutionally bless a specific implementation choice. Implementation choices are not constitutional choices. A preference for a specific technology, architecture, or operational pattern does not create a constitutional warrant for a new document.

**Exclusion 3 — Authority Expansion:** The desire to create new constitutional authority that the current stack does not assign. Authority expansion is governed by D7's Constitutional Amendment Architecture (D7 Part 12) — not by adding new documents outside that process.

### 12.3 Process for Future Documents

Future constitutional documents must be produced through the Constitutional Amendment Architecture established in D7 Part 12. The production of a new document is constitutionally equivalent to a Class II Structural Amendment (D7 Part 12.5) to the constitutional stack as a whole, requiring:

- Amendment Proposal with all six required elements (D7 AP-1 through AP-6)
- Deliberation through the D7 Deliberation Architecture
- Preservation Audit confirming the new document does not contradict any existing document
- Authorization from founding operators with D-2-level authority
- Publication with explicit notation of what the new document addresses and what it leaves for the existing stack
