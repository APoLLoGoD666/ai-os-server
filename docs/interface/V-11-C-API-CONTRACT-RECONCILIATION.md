# V-11-C API Contract Reconciliation

**Status:** CERTIFIED  
**Date:** 2026-09-01  
**Scope:** Backend API / error semantics + state contract (no frontend visual changes, no production deployment)

---

## Canonical Response Contract

### Success

Existing successful payload structures are **preserved** where frontend consumers depend on them. V-11-C does not blindly wrap every success response.

Example minimal success:
```json
{ "ok": true, "data": [...] }
```

Routes that already returned `{ ok: true, ...route-specific fields }` retain their shape.

### Canonical Error

Every API error response must conform to:
```json
{
  "ok": false,
  "error": "<CANONICAL_ERROR_CODE>",
  "message": "<human-readable explanation>",
  "requestId": "<correlation-id>"
}
```

- `error` — machine-readable, one of the controlled vocabulary codes below
- `message` — human-readable, safe (no stack traces, no DB internals)
- `requestId` — correlation ID, echoed from `X-Request-ID` header (set by `middleware/request-context.js`)

## Canonical Error Vocabulary

Defined in `lib/api-error.js`:

| Code | HTTP | Use |
|------|------|-----|
| `AUTHENTICATION_REQUIRED` | 401 | No valid session |
| `FORBIDDEN` | 403 | Authenticated but not authorised |
| `RATE_LIMITED` | 429 | Rate limit exceeded |
| `VALIDATION_ERROR` | 422/415 | Bad input / wrong content-type |
| `NOT_FOUND` | 404 | Route or resource does not exist |
| `CONFLICT` | 409 | Resource conflict |
| `DEPENDENCY_UNAVAILABLE` | 503 | External service unavailable |
| `DATABASE_UNAVAILABLE` | 500 | Database query failed |
| `INTERNAL_ERROR` | 500 | Unclassified server error |
| `TIMEOUT` | 504 | Request or dependency timed out |
| `SERVICE_DEGRADED` | 503 | Service operating in degraded mode |

---

## HTTP Semantics

| Status | Meaning | Implementation |
|--------|---------|----------------|
| 200 | Success (including legitimate empty datasets) | Unchanged |
| 401 | Authentication required | `_bootIdentity()` handles redirect |
| 403 | Forbidden | Route guards return `FORBIDDEN` |
| 404 | Route or resource not found | Inline 404 handler, server.js |
| 415 | Wrong content-type | `middleware/request-context.js` guard |
| 429 | Rate limited | All rate limiters — canonical handler |
| 500 | Internal error | Generic error handler, server.js |

**Guaranteed:** A genuine database failure NEVER returns `[]`, `{}`, `null`, or HTTP 200.

---

## Empty vs Error Distinction

This is enforced at all migrated routes:

| Scenario | HTTP | Body |
|----------|------|------|
| Query succeeds, zero rows | 200 | `{ ok: true, data: [], count: 0 }` |
| Database unavailable | 500 | `{ ok: false, error: "DATABASE_UNAVAILABLE", ... }` |
| Query parameter selects empty set | 200 | `{ ok: true, opportunities: [], count: 0 }` |
| Column missing from schema | 500 | `{ ok: false, error: "DATABASE_UNAVAILABLE", message: "...", requestId: "..." }` |

Frontend (`_parseApiError` in V-11-B) can now reliably distinguish EMPTY from FAILED.

## Request ID Behaviour

- `req.requestId` is generated by `middleware/request-context.js` for every request
- Format: `${Date.now().toString(36)}-${random5chars}` or `X-Request-ID` header if provided
- Echoed in `X-Request-ID` response header
- All canonical error responses include `requestId` in body
- Rate limiter handler uses fallback `${Date.now().toString(36)}-rl` if `req.requestId` not yet set (due to middleware ordering)

## Known Blocked Migrations

### evidence_refs column — NOT a migration

**Finding:** The `opportunities` table has NO top-level `evidence_refs` column (confirmed via migration audit: migrations 015, 017 — column never added). The field is stored as `roi_forecast.evidence_refs` (jsonb nested).

**Resolution:** Route SELECT was incorrect. Fixed by changing SELECT from `evidence_refs` (non-existent) to `roi_forecast` (which contains it). This is an **application fix**, not a schema migration.

**Schema migration required:** NO — the data is already in the correct location.

## V-11-B Integration

`_parseApiError(resp, json)` in V-11-B reads:
1. `json.message` — now populated on all migrated routes
2. `json.reply` — fallback for unmigrated routes (still works)
3. `json.error` (string) — already canonical field name

After V-11-C, canonical routes satisfy the target end state:
```javascript
return { code: json.error, message: json.message, requestId: json.requestId }
```

Unmigrated routes still fall back to the `reply` branch — no regression.
